# 4.8 Command line

The IDE can be used without its window. Started in a terminal with one of two commands, it does its work, prints to
the terminal and ends. `validate` checks a project. `run` validates a project, then runs it together with its bridges
in the IDE's Docker container and prints what happens until it is stopped.

## 4.8.1 Commands

```text
Usage:
  karpfen-ide [<folder>]
  karpfen-ide validate <folder> [--format text|json]
  karpfen-ide run <folder> [--descriptor <file>] [--bridge <file>]... [--capture] [--verbose]
```

| Command | Effect |
|---|---|
| `karpfen-ide <folder>` | Opens the window on the folder. Without a folder the window opens on its welcome view. |
| `karpfen-ide validate <folder>` | Validates the whole project, prints the findings and ends. |
| `karpfen-ide run <folder>` | Validates the project, runs it and prints what happens until it is stopped. |
| `karpfen-ide validate --help`, `karpfen-ide run --help` | Prints the usage and ends with status 0. `-h` does the same. |

The arguments follow these rules.

- Options may stand before or after the folder.
- The value of an option is the next argument, or it is attached to the option with `=` as in
  `--bridge=http.kbridge.json`.
- Everything after `--` is taken as the folder and not as an option. This is the way to name a folder that starts
  with `-`.
- A folder that is itself called `validate` or `run` would be read as the command when it is the first argument. Write
  it with a path in front, for example `./run`.

A wrong command line prints `karpfen-ide:` followed by what is wrong and then the usage. Both go to the error output,
and the command ends with status 2. The following counts as wrong.

- an unknown option
- no folder, a second folder or an empty folder name
- a folder that does not exist
- an option without its value
- a second `--descriptor` or a second `--format`
- a format other than `text` or `json`
- a bridge that is named twice
- an option that the command does not take

```text
karpfen-ide: unknown option '--frmat'
```

## 4.8.2 Starting it

| From | Command |
|---|---|
| The sources | `./gradlew :app:ide:run --args="validate /absolute/path/to/project"` |
| The application on macOS | `karpfen-ide.app/Contents/MacOS/karpfen-ide validate <folder>` |
| The application on Linux | `karpfen-ide/bin/karpfen-ide validate <folder>` |
| The application on Windows | `karpfen-ide\karpfen-ide.exe validate <folder>` |

From the sources the folder must be an absolute path. `./gradlew :app:ide:createDistributable` builds the application
into `app/ide/build/compose/binaries/main/app/`.

On Windows the application is built with a console because the commands need somewhere to print. As a consequence a
console window also opens when the IDE is started by a double-click.

## 4.8.3 Validating

```bash
karpfen-ide validate examples/lamp
```

The command runs the same checks of [4.4 Validating](4.4-validating.md) as the button *Validate* in the window. It
prints one line per finding with the errors first, and a summary as the last line. For a project without findings the
whole output is the line `No problems found.`

```text
lamp.kstates:13: error: mismatched input 'STATMACHINE' expecting 'STATEMACHINE'
switch.kstates:8: warning: This EVAL has no return, so it yields no value; return the value it computes
1 error and 1 warning
```

Which of the optional [4.1.7 Language features](4.1-projects.md#417-language-features) are on is read from the
`.karpfenproject` file of the folder, exactly as the window reads it, and the keys of that file are listed in
[4.1.6 The project file](4.1-projects.md#416-the-project-file). The state machines of the spares example project use
macros, and `karpfen-ide validate examples/spares` accepts them because the project file of the example switches
macros on.

Since a finding about a `behaves after` belongs to the metamodel, it is printed with the file and the line of the
`.kmeta` file, for example `spares.kmeta:4: error: ...`.

For a program that reads the result, `--format json` prints one JSON document in place of the lines.

```bash
karpfen-ide validate examples/lamp --format json
```

```json
{
    "root": "/home/me/karpfen-IDE/examples/lamp",
    "errorCount": 1,
    "warningCount": 1,
    "problems": [
        {
            "path": "lamp.kstates",
            "line": 13,
            "column": 1,
            "severity": "error",
            "message": "mismatched input 'STATMACHINE' expecting 'STATEMACHINE'",
            "code": "syntax-error"
        },
        {
            "path": "switch.kstates",
            "line": 8,
            "column": 33,
            "severity": "warning",
            "message": "This EVAL has no return, so it yields no value; return the value it computes",
            "code": "kstates.eval-without-return"
        }
    ]
}
```

| Member | Meaning |
|---|---|
| `root` | The folder of the project, as an absolute path. |
| `errorCount`, `warningCount` | How many errors and warnings the project has. |
| `problems` | The findings, sorted by path, line and column. |
| `path` | The file, relative to the folder. |
| `line`, `column` | Where the finding starts. Both count from 1. |
| `severity` | `error`, `warning`, `info` or `hint`. |
| `message` | What is wrong, in words. |
| `code` | The stable name of the kind of finding. |

## 4.8.4 Running

```bash
karpfen-ide run examples/lamp --descriptor lamp.kenv.json --bridge http.kbridge.json --capture
```

| Option | Meaning |
|---|---|
| `--descriptor <file>` | The descriptor to run, relative to the folder or absolute. It can be left out when the project has exactly one. |
| `--bridge <file>` | A bridge file of the project to start with the run. Give the option once per bridge. Without it no bridge starts. |
| `--capture` | Writes the log of the run to a file in `karpfen-runs/`. This is what the checkbox *Capture run to file* does in the window, and the files are the ones of [4.5.8 Captured logs](4.5-running.md#458-captured-logs). |
| `--verbose` | Also prints every line of the runtime's log. |

Before anything starts, the command checks the chosen files against the project. If a file does not fit, the command
prints one of the messages below and the usage and ends with status 2, as for a wrong command line.

| Case | Message |
|---|---|
| The project has no descriptor. | `the project has no environment descriptor (*.kenv.json)` |
| The project has several descriptors, and `--descriptor` is missing. | `the project has several environment descriptors; choose one with --descriptor:` and the list |
| `--descriptor` names no descriptor of the project. | `<file> is no environment descriptor of the project;` and the list |
| `--bridge` names no bridge file of the project. | `<file> is no bridge file of the project;` and the list |

A run goes through these steps.

1. It validates the whole project. If the project has an error, the findings are printed as by `validate` and the run
   does not start. Warnings alone do not hold a run back. They are printed in the same way, followed by the line
   `The run goes on despite the warnings.`
2. It starts the runtime in the IDE's Docker container. The first run builds the runtime image.
3. It deploys the descriptor and starts the bridges.
4. It prints what happens until you stop it with Ctrl+C or a terminate signal.
5. It stops the bridges and the environment, removes the runtime container and ends.

Step 5 stops the environment and then drops it. Dropping removes the environment from the runtime, and it happens
before the container is removed.

A run does not have to be stopped from the terminal. If another client of the runtime stops or drops the environment,
the run notices it, prints `The run ended on its own.` and ends with status 3.
[4.5.5 Stopping a run](4.5-running.md#455-stopping-a-run) describes the same case for the window.

| `<bridge file>: ...` | The state of a bridge. Once the bridge runs, the line also says how many messages it took in and sent out. |
| `<time>  <object>  <text>` | A line of the simplified log, as the *Log* pane shows it. |
| `<severity>: <file>:<line>:<column>: <message>` | A problem of the preparation or the run. |
| `[stdout] ...`, `[stderr] ...` | A line of the runtime's log, with `--verbose`. |
| `Captured to karpfen-runs/<file>` | Where the run is captured. |
| `Stop requested.`, `Shutting down ...`, `Shut down.` | The end of the run. What the bridges and the runtime say while they stop stands in between. |

For each definition of a descriptor the run has a step `Uploading the definition <file>`. While the run goes on,
objects get and lose instances of these definitions in the way that
[4.5.4.7 State machine instances](4.5-running.md#4547-state-machine-instances) describes, and the simplified log has a
line for each such change.

| Change | Line of the simplified log |
|---|---|
| An object gets an instance. | `bulb  attaches glowing` |
| The instance of an object is exchanged for another. | `bulb  exchanges glowing for flickering` |
| An object loses its instance. | `bulb  detaches flickering` |

When the event `flicker` comes in, a run of the spares example project prints, among others, these lines.

```text
bulb (glowing): lit
spare (glowing): lit
14:20:16.500  bulb  exchanges glowing for flickering
14:20:16.501  bulb  starts in on
bulb (flickering): on
```

For each fragment of a descriptor the run has a step `Uploading the fragment <file>`. A state of a fragment is printed
with the name of its container state in front, because that is the name the state has in the running state machine
of [4.5.4.8 Pages](4.5-running.md#4548-pages). A run of the pages example project prints lines such as this one.

```text
lamp: self test > self test/wiring > self test/wiring/measuring
```

A run that does not get going says why and ends with one of these lines.

| Line | Status |
|---|---|
| `The run does not start: the project has errors.` | 1 |
| `The run did not start.` | 3 |
| `The run does not start: the deployment is blocked.` | 3 |
| `The run failed.` | 3 |
| `The run ended on its own.` | 3 |

## 4.8.5 What a run reads from the project

The only thing a run without a window reads from `.karpfenproject` is the set of features that are switched on. This
includes the optional language features as well as the features of the project such as Parallel branches on threads.
All other entries of the file are ignored. That holds for the bridges ticked in the window too, because on the command
line the bridges are chosen with `--bridge`.

The run never writes to `.karpfenproject` or to the settings of the user.

Since there is no debugger without a window, a breakpoint does not halt the run, even if the project has breakpoints
switched on. There is no time limit either. The run goes on until it is stopped with Ctrl+C or a terminate signal.

## 4.8.6 Exit statuses

| Status | Meaning |
|---|---|
| 0 | The validation found no error. Warnings are allowed. Also after `--help`. |
| 1 | The project has errors. A run did not start. |
| 2 | The command line was wrong. A message and the usage are printed. |
| 3 | A run could not start, failed or ended on its own, or the folder could not be opened as a project. |

A run that is stopped by a signal ends with the status the system gives a process that got that signal. Since that
status is not 0, a run started through Gradle makes the Gradle task fail when it is stopped.

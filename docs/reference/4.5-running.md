# 4.5 Running

The menu entry *Run > Run* deploys an environment descriptor to a karpfen runtime and starts it. The IDE runs the
runtime in a Docker container of its own. While the model runs, the *Runtime* tool window shows the model as it changes,
the events, the active states and the log of the runtime. What the runtime does with a model is described in
[3 Execution](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3-execution.md).

## 4.5.1 The runtime container

Since a model runs only in the IDE's own Docker container, Docker Desktop or another local Docker engine has to be
running before a run.

- Each open folder gets its own container. The container listens only on `127.0.0.1`, on a free port.
- The first run builds the runtime image from the runtime that comes with the IDE. This takes a few minutes, and only
  once.
- The image holds Python 3 for the `EVAL` blocks, with the packages numpy, scipy, sympy, pandas, regex,
  python-dateutil and chardet.
- The container starts with the first run. It keeps running after the run stops, and the next run starts fast because
  it does not have to wait for a new container.
- Closing the folder or the IDE stops and removes the container. The image stays.

The menu entry *Run > Start Runtime* starts the container without a run, and *Run > Stop Runtime* stops and removes
it. The buttons *Start runtime* and *Stop runtime* in the *Runtime* tool window do the same. The containers and the
image carry the label `io.karpfen.ide.runtime=true`.
[1.12 Closing and cleaning up](1-getting-started.md#112-closing-and-cleaning-up)
shows the commands that remove them by this label.

Running a model on a runtime of your own, without the IDE, is described in
[3.3 Running the runtime](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.3-running-the-runtime.md).

## 4.5.2 Starting a run

*Run > Run* (Shift+F10) starts a run. On a Mac keyboard you may have to hold Fn to get F10. The run goes through these
steps.

1. It picks the descriptor. This is the descriptor in the active editor or else the only descriptor of the project.
   Otherwise it asks in the dialog *Run* with the sentence `Choose the environment descriptor to run:`, and the last
   choice is selected. A project without a descriptor gets an error that says how to create one.
2. It saves every open file, because it uploads the saved files.
3. It validates the whole project. An error blocks the run as described in
   [4.4.6 Validation before a run](4.4-validating.md#446-validation-before-a-run).
4. It opens the run dialog.
5. It stops an earlier run of the same descriptor that still runs.
6. It prepares the deployment from the saved files and checks it.
7. It starts the container if it is not running and waits for the runtime.
8. It deploys the descriptor and starts the environment.

## 4.5.3 The run dialog

The dialog *Run* opens with every run, also with the button *Run again*.

| In the dialog | Effect |
|---|---|
| One box per bridge file of the project | The ticked bridges of [4.7 Bridges](4.7-bridges.md) start with the run. |
| *Capture run to file* | The run writes the whole log of the runtime to a file as described in [4.5.8 Captured logs](#458-captured-logs). |
| *Run*, *Cancel* | Starts the run, or ends it here. |

The boxes ticked last time are ticked again, because the choices are kept in `.karpfenproject`.

## 4.5.4 The Runtime tool window

The *Runtime* tool window opens with every run and then takes three quarters of the window's height. The status bar
shows the state of the runtime as `Runtime: stopped`, `building image`, `starting`, `running`, `failed` or `stopping`. A
click on it shows the tool window.

The button at the right end of the title bar of the tool window moves the tool window into a window of its own. That
window can be placed anywhere, for example on a second screen. The place of the tool window in the main window closes,
and the editor gets the room.

In the separate window the same button shows the dock icon. It moves the tool window back to its place in the main
window, with the height it had before. Closing the separate window also docks the tool window. Since the separate window
has the same menus as the main window, *Run > Run*, *Run > Stop* and the keys of the debugger work there too. It follows
the theme and the zoom of the main window, and it closes with the project and with the main window.

While the tool window is detached, a new run, a click on the runtime status in the status bar and *View > Runtime* show
it in its own window and bring that window to the front. If the tool window is shown, *View > Runtime* hides it and
closes the separate window. Showing it again opens the separate window again, because the tool window stays detached
until it is docked.

When the tool window moves between the two places, the runs, the selected run, observation and the log carry over. The
scroll positions and the widths of the *Model*, *Events* and *Log* panes start anew.

Whether the tool window is detached is kept in `.karpfenproject`, in a line such as `pane.runtime = shown 400 detached`
among the keys that [4.1.6 The project file](4.1-projects.md#416-the-project-file) lists.
A project that was closed with the tool window detached opens it in its own window again. The place and size of the
separate window are kept in `~/.karpfen-ide/settings.json`. If that place lies on a screen that is no
longer connected, it is dropped, and the window opens in the middle of the screen.

### 4.5.4.1 The runtime line

The first line of the tool window says what the container does. It also holds the buttons *Start runtime* and
*Stop runtime*.

| Text | Meaning |
|---|---|
| `Docker: not started` | No container runs. |
| `Docker: checking the Docker engine` | The IDE looks for the Docker engine. |
| `Docker: building the runtime image` | The first run builds the image. A detail of the build step may follow. |
| `Docker: creating the container`, `Docker: starting the container` | The container is being set up. |
| `Docker: waiting for the runtime` | The container runs, and the runtime in it starts. |
| `Docker: running at 127.0.0.1:<port>` | The runtime is ready. |
| `Docker: stopping` | The container is being stopped and removed. |
| `Docker: <problem>` | The container could not be started. The text is red and can be selected. |

### 4.5.4.2 The runs

The second line lists the runs. Each run shows its name, the key of its environment once that is known, and its phase.
The name is the file name of the descriptor without `.kenv.json`. A click selects a run, and the panes below show the
selected run.

| Phase | Meaning |
|---|---|
| `preparing` | The run prepares the deployment from the saved files. |
| `blocked` | The preparation found errors. The run never reached the runtime. |
| `waiting for the runtime` | The run waits for the container. |
| `deploying` | The run uploads the files and configures the environment. |
| `running` | The environment runs. |
| `ready` | The environment is activated but not started. |
| `stopped` | The environment was stopped. |
| `failed` | The runtime, the deployment or the environment failed, or the environment ended on its own. |

The runs are followed by the buttons *Run again*, *Stop* and *Clear finished*. *Run again* starts the selected run anew
and goes through the steps of [4.5.2 Starting a run](#452-starting-a-run). *Stop* stops the selected run.
*Clear finished* removes every run that is blocked, stopped or failed from the list.

With breakpoints switched on, a third line holds the debugger of [4.6 Debugging](4.6-debugging.md).

Below these lines the panes *Model*, *Events* and *Log* show the selected run side by side.

### 4.5.4.3 The Model pane

The *Model* pane shows the model of the running environment as a tree. Its buttons *Expand all* and *Collapse all*
open and close every row.

| Row | Meaning |
|---|---|
| `relation: key : Type` | An object, under the relation that holds it. |
| `name = value` | A property and its value. |
| `relation -> key` | A `knows` reference. A click on the key selects that object. |
| `created at run time` | Marks an object that the state machines created. |

The switch *Observation* decides how the tree follows the run. With observation on, the runtime reports every change,
and the tree, the active states and the statecharts follow at once. With observation off, the tree stays as it is, and
the button *Pull* reads the current model once. A run starts with observation on.

The status next to the switch reads, for example, `Observation on, live at revision 12` or
`Observation off, pulled at revision 30`. It can also read `predicted, nothing read yet` or `synchronizing`, and after
the environment has stopped it reads `final at revision N`. Once a run has ended, the switch and *Pull* are greyed out
because the runtime no longer holds its environment.

### 4.5.4.4 The Events pane

The *Events* pane sends events into the run and lists the events of the environment.

1. Under *1. Domain*, choose a domain. The domains are those the state machines use. A domain with an event that the
   event metamodel declares is in bold. A domain whose events no event metamodel declares is marked `(used only)`.
2. Under *2. Event*, choose an event. Each event reads as `name: PayloadType`, or with `(used only)` if the event
   metamodel does not declare it.
3. Under *3. Payload*, edit the payload as JSON. It starts as a template of the payload type and is checked after every
   change. For an event without a payload type the field reads
   `This event has no payload type. It is sent without a payload.`
4. Click the button that reads *Send* followed by the name of the event, for example *Send press*. The button is
   greyed out while the payload has an error or while events cannot be sent.

After a send, the line next to the button reads `Sent. It shows in the list below once the runtime has published it.`
or `Not sent:` with the reason. A line below it says whether events can be sent at the moment.

| Text | Meaning |
|---|---|
| `Events cannot be sent yet, because the environment is not deployed.` | The deployment has not reached the environment. |
| `The environment has not started yet. An event sent now waits until it starts.` | The environment is activated but not started. |
| `The environment is running. An event is delivered at once.` | Events go in now. |
| `Events cannot be sent:` and a reason | The run has ended or the connection is lost. |

The list `Events in this environment, newest first` shows the events sent from here, from other clients and from
bridges, as well as the events that the state machines raise. Its columns are *Time*, *Domain*, *Event*, *Source* and
*Payload*. The source is `external` for an event from outside and `internal` for an event that a state machine raised. A
click on an event shows its whole payload. An empty list reads
`No events yet. Events you send and events the state machines raise appear here.`

An event waits until a state machine takes it or until its time to live runs out. The time to live is the key
`eventTtlMs` of the descriptor in
[4.1.2 Environment descriptors](4.1-projects.md#412-environment-descriptors). How the runtime hands events to the
state machines is described in
[3.1 Execution semantics](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md).

### 4.5.4.5 The Log pane

The *Log* pane has the controls *Simplified*, *Follow* and *Clear*. *Simplified* is a switch that is on at first, and
*Follow* keeps the newest line in sight. Above the log the pane shows what the run has to tell.

- `The runtime could not be started:` with the problem of the container.
- `Captured to karpfen-runs/<file>` when the run is captured, or `The run could not be captured to a file:` with the
  reason.
- `Findings that block the run` with the problems of the preparation. A click on one leads to its place.
- The active states of each state machine instance with the outermost state first, for example `lamp: on > full`. An
  instance of a definition also names its definition, for example `gen_Bulb_0 (glowing): lit`. Where such instances
  come from is explained in [4.5.4.7 State machine instances](#4547-state-machine-instances).
- One line about the deployment, for example `Deployment done, 16 steps`, `Deploying: <step>` or
  `Deployment failed at: <step>`. A click on it shows the details with the environment, the connection, every step
  and the problems of the run.
- One line per bridge of the run as described in
  [4.7.6 The bridges of a run](4.7-bridges.md#476-the-bridges-of-a-run).

All of this text can be selected and copied.

With *Simplified* on, the log shows only the steps of the state machines and the errors. Each of them gets one line with
the time, the object or `engine`, and the text.

```text
14:17:03.887  lamp        attaches its state machine
14:17:03.888  lamp        starts in off
14:17:03.889  wallSwitch  attaches its state machine
14:17:03.890  wallSwitch  starts in down
14:17:03.892  engine      Engine started with 2 state machine(s), tickDelay=500ms
14:17:03.895  lamp        runs the entry actions of off
14:17:04.896  lamp        off -> full
14:17:04.898  wallSwitch  down -> up
14:17:05.397  lamp        runs the entry actions of on
14:17:05.399  lamp        runs the entry actions of full
```

The times are those of the clock of the runtime. In the container this clock runs in UTC.

A split makes a state machine run on several paths at once until a join brings them together again, and
[2.3.4.3 Splits and joins](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#2343-splits-and-joins)
defines both. The runtime numbers the paths of each object. While an object runs on more than one path, each of its
lines begins with the path it belongs to. The lines of the split and of the join name the paths that they start and end.

```text
14:17:04.896  lamp        split off -> test bulb, test switch into paths 1, 2
14:17:04.898  lamp        path 1: runs the entry actions of test bulb
14:17:04.899  lamp        path 2: test switch -> check position
14:17:05.397  lamp        join bulb ok, switch ok -> on from paths 1, 2
14:17:05.399  lamp        runs the entry actions of on
```

An object that runs on one path shows no path, and a run without splits never shows one.

An empty simplified log reads
`No step of a state machine yet. Switch Simplified off to see the whole output of the runtime.` With *Simplified* off,
the log shows every line of the output of the runtime, and the lines of its error output are red.

### 4.5.4.6 The deployment steps

The details of the deployment list each step with its state and a detail. The state is `pending`, `running`, `done`,
`skipped` or `failed`. A run of the lamp example project goes through sixteen steps.

```text
Checking the runtime at http://127.0.0.1:65457: done, The runtime is up and supports the IDE
Creating the environment: done, env-1794579423685
Connecting to the environment: done, Connected as karpfen-ide-254666e10161
Uploading lamp.kmeta: done
Uploading lamp-events.kmeta: done
Uploading lamp.kmodel: done
Attaching lamp.kstates to lamp: done
Attaching switch.kstates to wallSwitch: done
Setting the tick delay to 500 ms: done
Setting the event time to live to 5000 ms: done
Listening to 2 event domains: done, service, switch
Switching on runtime features: skipped, The project switches on no language feature that needs one
Activating the environment: done
Switching observation on: done, The runtime read the model as analyzed
Starting the environment: done
Confirming the start: done, Every state machine reported its state
```

A descriptor with definitions has a step such as `Uploading the definition glowing.kstates` for each definition. These
steps stand among the attaching steps, in the order of the descriptor. The step Confirming the start waits for every
instance that the start built, the instances of the definitions included.

A descriptor with fragments has a step such as `Uploading the fragment bulb_test.frag.kstates` for each fragment, also
in the order of the descriptor. What the runtime makes of the fragments is described in [4.5.4.8 Pages](#4548-pages).

The step that switches on runtime features names the features that the project needs. With histories and tick limits
switched on, it reads `Switching on History, TickLimit`. With Parallel branches on threads switched on as well, it
reads `Switching on History, TickLimit, TrueParallel`. Which runtime feature each language feature needs is listed in
[4.1.7 Language features](4.1-projects.md#417-language-features). A runtime that does not know TrueParallel is older
than the IDE, and it fails the step with
`The runtime at <address> does not know the feature TrueParallel, so it is older than the IDE.`

### 4.5.4.7 State machine instances

A run has one state machine instance for each object that runs a state machine. The descriptor attaches state
machines to objects by their keys, and it lists attachable state machines as the definitions of
[4.1.2.3 Definitions](4.1-projects.md#4123-definitions).

The runtime gives objects instances of definitions and takes them away while the run goes on, by the rules of
[3.1.13 State machine management and lifecycle](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md#3113-state-machine-management-and-lifecycle).

- At the start, each object whose type behaves after a definition gets an instance of it.
- An object that a rule creates gets an instance of the definition its type behaves after, or of the one its `ATTACH`
  names.
- `EXCHANGE` ends the instance of an object and gives the object an instance of another definition. The new instance
  starts in its initial state.
- An object that leaves the model takes its instance with it.

The *Runtime* tool window follows the instances. The active states above the log name the object and, for an instance of
a definition, the definition in parentheses. A new instance shows the initial state of its definition until its first
step. An instance that ends disappears together with its states. The diagram of a definition shows one instance at a
time, and [4.3.10 While a model runs](4.3-diagrams.md#4310-while-a-model-runs) explains how to choose it.

With *Simplified* on, the log says when an object gets or loses an instance.

```text
14:20:11.000  bulb        attaches glowing
14:20:11.001  bulb        starts in lit
14:20:16.500  bulb        exchanges glowing for flickering
14:20:16.501  bulb        starts in on
14:20:18.500  gen_Bulb_0  attaches glowing
14:20:18.501  gen_Bulb_0  starts in lit
14:20:19.000  bulb        detaches flickering
```

At each start the log has an `attaches` line for every instance. For a state machine that the descriptor attached, the
line reads `attaches its state machine`. When an `EXCHANGE` ends such a state machine, the log reads
`exchanges its state machine for flickering`. The initial state of an instance follows right after the line that gives
the object the instance.

The preparation checks the definitions against the descriptor before anything reaches the runtime.

- A type that behaves after a state machine that the descriptor does not list blocks the run with
  `deploy-definition-not-listed`, because the runtime would refuse to activate the environment.
- An `ATTACH` or `EXCHANGE` that names a state machine the descriptor does not list gives the warning
  `deploy-attached-definition-not-listed` at the state machine. The runtime fails such an action when it runs and
  writes the failure to its log. A name that an `EVAL` or a `MACRO` computes is not checked.

The spares example project in `examples/spares` shows all of this.

- Each bulb runs `glowing` from the start.
- The event `stock` of the domain `service` puts a new bulb with `glowing` on the shelf.
- `flicker` exchanges the state machine of the bulb in the lamp for `flickering`.
- `replace` screws in a new bulb, and the old bulb leaves with its instance.

### 4.5.4.8 Pages

A state machine composed of the pages of
[2.3.12 Pages](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#2312-pages)
has container states that run fragments. The descriptor lists every fragment that a run needs, without `attachedTo`,
including the fragments that only other fragments use, as in the descriptor of
[4.1.2.5 Fragments](4.1-projects.md#4125-fragments).

The deployment uploads each fragment as it stands before it activates the environment. When the runtime activates the
environment, it puts the fragments into the container states and runs one flat state machine for each object.

In the flat state machine the states of a fragment carry the name of their container state in front, separated by a
slash. In the pages example project in `examples/pages`, the container state `self test` of the lamp uses
`bulb_test`, and the container state `wiring` of `bulb_test` uses `wiring_check`. The states inside `self test` read
`self test/wiring` and `self test/wiring/measuring`.

The *Runtime* tool window uses these names everywhere it names states. These places are the active states above the log,
for example `lamp: self test > self test/wiring > self test/wiring/measuring`, the simplified log and the debugger line.
A fragment that two container states use runs as two copies, and each copy carries the name of its own container
state.

The preparation checks the pages against the descriptor before anything reaches the runtime.

- If a state machine of the run uses a fragment that the descriptor does not list, directly or through another
  fragment, the run is blocked with `deploy-fragment-not-listed` at the descriptor. The problem names the fragment,
  its file and the file that uses it. The validation of [4.4 Validating](4.4-validating.md) runs before the
  preparation and reports the same cause as `project.unknown-fragment`.
- A composition that does not flatten blocks the run with `deploy-not-flattened` at the state it concerns. The message
  is the one of dsl-tools. Examples are a container state that uses an attachable state machine and a macro that two
  files of the composition define differently.

If the runtime refuses the activation nevertheless, the run fails. It then has one problem per line of the refusal, in
the words of the runtime, at the file of the state machine that the line names.

How the statecharts show a run in pages is described in
[4.3.10 While a model runs](4.3-diagrams.md#4310-while-a-model-runs).

## 4.5.5 Stopping a run

The button *Stop* in the line of the runs, or *Run > Stop* (Cmd+F2 / Ctrl+F2), stops the selected run. The run turns
`stopped`. The *Model* pane keeps the last model, and the button that sends events is greyed out. The container keeps
running. A new run of the same descriptor also stops the run before it.

A stop ends the run for good. The IDE reads the model a last time and then drops the environment, and the runtime
forgets the environment and no longer lists it. *Run again* deploys a fresh environment. By itself the runtime would
only freeze a stopped environment, by the rules of
[3.1.13.9 Stop and start, forcing and clients](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md#31139-stop-and-start-forcing-and-clients).

Every way a run ends drops its environment in the same way.

- *Stop*
- a new run that replaces the run before it
- closing the project
- *Stop runtime*
- quitting the IDE
- the end of a run on the command line

Since the IDE asks the runtime nothing more about the environment after the drop, the *Model* pane, the *Events* pane,
the debugger and the bridges show what the run saw last.

A drop can fail, for example because the runtime is gone or because it is an older runtime that cannot drop
environments. The run still ends as `stopped`, and the *Log* pane notes the problem `environment-left-behind` with the
reason, for example
`The runtime at http://127.0.0.1:65457 cannot drop environments, so it is older than the IDE; the environment env-1794579423685 stays there.`
The IDE waits at most ten seconds for a drop.

Another client of the runtime can stop the environment of a run as well. The run then also turns `stopped`. The *Log*
pane notes `The runtime reports that the environment stopped.` and says that somebody other than the session stopped
the environment and that the run has ended. The IDE then reads the model a last time and drops the
environment as after its own stop.

If another client drops the environment of a run, the run turns `stopped` as well. The *Log* pane notes that somebody
other than the session dropped the environment and that the run has ended. Since nothing of the environment
is left to read, the *Model* pane keeps what the run saw last.

If the runtime ends while a run is live, for example because its container was removed outside the IDE, the run turns
`failed` with the problem `environment-lost`.

## 4.5.6 A failed run

A run can end before or after it reaches the runtime.

| What happens | Where it shows |
|---|---|
| The project has errors. | The dialog `Run Blocked: the Project Has Errors`, described in [4.4 Validating](4.4-validating.md). |
| The preparation finds a problem, such as a state machine attached to a missing key. | The run is `blocked`, and the *Log* pane lists the problems under `Findings that block the run`. |
| Docker is not running. | The run is `failed`. The runtime line and the *Log* pane read `Cannot connect to the Docker engine at ...` and `Start Docker Desktop or the local Docker engine, then try again.` |
| The container stopped. | The runtime line names the container and asks to run again. |
| A step of the deployment fails. | The run is `failed`, and the *Log* pane reads `Deployment failed at: <step>`. The details list the problems. |
| The runtime refuses an uploaded file. | One problem per error of the file at its line and column, for example `lamp.kstates:13:1: <message>`. A click leads to the place. |
| The runtime refuses the form of a state machine. | One problem at the file with the runtime's text, for example `A state machine without attachedTo must have the attachable form ...`. |
| The runtime refuses to activate the environment, because a type behaves after a state machine it does not hold or that is not attachable to the type. | One problem at the descriptor with the runtime's text. |
| The runtime refuses to activate the environment, because a state machine does not flatten with the fragments it holds. | One problem per line of the runtime's text, at the file of the state machine it names, for example `The runtime refused the activation, because lamp.kstates cannot be flattened: <message>.` |
| The environment ends on its own. | The run is `failed` with the problem `engine-halted`. The log of the runtime has the reason. |

The problems of the preparation and the deployment have these codes.

| Code | Severity | Meaning |
|---|---|---|
| `deploy-no-context` | Error | The descriptor could not be read. Its own problems say why. |
| `deploy-save-failed` | Error | A file could not be saved before the deployment. |
| `deploy-unsaved-file` | Error | A file was edited while the run prepared. Run again. |
| `deploy-context-errors` | Error | A file of the context has errors. There is one problem per file, at its first error. |
| `deploy-no-metamodel`, `deploy-no-model` | Error | The context has no metamodel or no model, or it could not be read. |
| `deploy-unknown-attachment` | Error | A state machine is attached to a key that no object of the model has. |
| `deploy-definition-not-listed` | Error | A type behaves after a state machine that the descriptor does not list as a definition. |
| `deploy-attached-definition-not-listed` | Warning | An `ATTACH` or `EXCHANGE` names a state machine that the descriptor does not list as a definition. |
| `deploy-fragment-not-listed` | Error | A state machine of the run uses a fragment, directly or through another fragment, that the descriptor does not list. |
| `deploy-not-flattened` | Error | A state machine of the run does not flatten with the fragments the descriptor lists. |
| `deploy-duplicate-attachment` | Error | Two state machines are attached to the same key. |
| `deploy-attachment-type` | Warning | The attached object's type differs from the type after `ATTACHED TO`. |
| `deploy-reference-loop` | Error | An object is reachable from itself through `has` and `knows`. The runtime cannot read such a model. |
| `deploy-domain-is-attachment` | Warning | An event domain is named like an attached object key. |
| `deploy-tick-delay-range`, `deploy-tick-delay-zero`, `deploy-event-ttl-never-expires` | See [4.1.2.1 Keys](4.1-projects.md#4121-keys) | The timing of the descriptor. |
| `deploy-model-differs` | Warning | The model the runtime read back differs from the model the IDE read. There is one problem per object. |
| `runtime-unreachable` | Error | The runtime could not be reached. |
| `runtime-incompatible` | Error | The runtime does not answer like a karpfen runtime that supports the IDE. |
| `runtime-no-answer` | Error | The runtime did not answer in time, or the connection broke during a call. |
| `runtime-rejected` | Error | The runtime refused a call, with its reason. A refused upload gives one problem per error of the file. |
| `runtime-error` | Error | The runtime failed with an internal error. |
| `handshake-rejected` | Error | The runtime refused the WebSocket connection. |
| `connection-lost` | Error or warning | The connection could not be opened or was given up. After the deployment it is a warning. |
| `engine-halted` | Error | The environment ended on its own. |
| `engine-silent` | Warning | Not every state machine instance reported its state after the start. |
| `observation-out-of-sync` | Warning | Observation is on, but the model could not be read again. The tree stays as it was until the next *Pull*. |
| `environment-lost` | Error | The runtime no longer knows the environment, usually because it ended or restarted. |
| `environment-left-behind` | Info | An environment stays on the runtime, because dropping it failed or took too long. |

## 4.5.7 Several runs

Runs of different descriptors can run at the same time in the same container. Each run has its own environment and its
own panes. The list of runs keeps every run until *Clear finished* removes it, and a finished run keeps its panes after
its environment was dropped.

## 4.5.8 Captured logs

With the checkbox *Capture run to file* ticked, the run writes the whole log of the runtime into the folder
`karpfen-runs` of the project. The file is named after the date and time of the start, for example
`2026-11-13_14-32-05.log`, and if the name is taken, `-2`, `-3` and so on are added. The folder does not show in the
*Project* tool window, because the IDE leaves the folder `karpfen-runs` out of the project. The *Log* pane names the
file of the selected run.

The file starts with lines that begin with `#`. They name the descriptor, the start, the address of the runtime and,
once it is known, the environment.

```text
# karpfen run capture
# Descriptor: lamp.kenv.json
# Started: 2026-11-13 14:32:05
# Runtime: the IDE's Docker container at http://127.0.0.1:65457
# Environment: env-1794579423685
```

Every line of the log of the runtime follows, from the deployment to the end of the run. This includes the lines of
each tick that the *Log* pane leaves out. Each line is marked `stdout` or `stderr`.

The file holds the log of the whole runtime for as long as its run lives. With two runs at once, each file
also holds the lines of the other run. Lines that the runtime writes before the deployment are not in the file.

# 4.1 Projects

A project is a folder. It is opened with *File > Open Folder…* (Cmd+O / Ctrl+O), and the submenu *File > Open Recent*
lists the folders opened before. The IDE reads every file below the folder and tells from each file name what kind of
file it is. It then groups the model files into contexts. A context is a set of files that are checked and run together.

## 4.1.1 Kinds of files

The kind of a file follows from its name alone.

| Name | Kind | Reference |
|---|---|---|
| `*.kmeta` | Domain metamodel | [2.1 KMeta](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.1-kmeta.md) |
| `EVENTS.kmeta`, in any case | Event metamodel | [2.1 KMeta](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.1-kmeta.md) |
| `*.kmodel` | Model | [2.2 KModel](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.2-kmodel.md) |
| `*.kstates` | State machine | [2.3 KStates](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md) |
| `*.frag.kstates` | Fragment, a page that container states of other state machines run | [2.3.12 Pages](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#2312-pages) |
| `*.kenv.json` | Environment descriptor | [4.1.2 Environment descriptors](#412-environment-descriptors) |
| `*.kbridge.json` | Bridge | [4.7 Bridges](4.7-bridges.md) |
| `*.vis` next to a model file | Layout of a diagram, written by the IDE | [4.3 Diagrams](4.3-diagrams.md) |
| `.karpfenproject` | Project file | [4.1.6 The project file](#416-the-project-file) |

An event metamodel may also have another name, such as `lamp-events.kmeta`, if a descriptor names it under `events`.

A fragment file holds one fragment, written `STATEMACHINE "name" FRAGMENT`, and is named after it. The fragment
`bulb_test`, for example, lives in `bulb_test.frag.kstates`. The language itself finds a fragment by its name alone and
never sees the name of its file. The file name is a convention of the IDE that keeps the files easy to find, and a
breach of it is therefore only a warning. The warning `fragment-file-name` is given in two cases.

- A fragment stands in a file whose name does not fit the name of the fragment, ignoring case. This includes a fragment
  in a plain `*.kstates` file. The warning stands at the name of the fragment.
- A fragment file holds a state machine that is not a fragment.

Apart from the warning, a fragment in a file with another name is read and runs the same as one in its own fragment
file.

The IDE leaves out the folders `.git`, `.gradle`, `build`, `out`, `.idea`, `.kotlin`, `node_modules` and
`karpfen-runs`, and every other folder whose name starts with a dot.

## 4.1.2 Environment descriptors

An environment descriptor is a JSON file named `*.kenv.json`. It says which metamodel, event metamodel, model and state
machines form one context, which object of the model each state machine is attached to, and how fast the model runs.
The menu entry *Run > Run* always starts a descriptor. The paths in the descriptor are relative to its folder, and they
must lie inside the project.

### 4.1.2.1 Keys

| Key | Value | Meaning |
|---|---|---|
| `metamodel` | String, required | The domain metamodel, a `.kmeta` file. |
| `events` | String or `null` | The event metamodel, a `.kmeta` file. Without it the context has no events. |
| `model` | String, required | The model the runtime starts from, a `.kmodel` file. |
| `stateMachines` | List of objects | The state machines. Each entry has `file`, a `.kstates` file, and `attachedTo`, the key of the object it runs on. The type of that object should be the type after `ATTACHED TO` in the state machine. An entry without `attachedTo` names an attachable state machine or a fragment. The environment keeps an attachable state machine as a definition as described in [4.1.2.3 Definitions](#4123-definitions). Fragments are described in [4.1.2.5 Fragments](#4125-fragments). Without the key the list is empty. |
| `tickDelayMs` | Number | The time in milliseconds between two ticks. Without the key it is 50. |
| `eventTtlMs` | Number | How long in milliseconds an event waits for a state machine that takes it. 0 keeps events until a state machine takes them. Without the key it is 3000. |
| `observe` | Object | Holds `objects` and `domains`. `objects` is required and may be `"*"` for every object. `domains` is a list of event domains. A run does not use it, because the IDE observes the whole model and listens to every domain the state machines use. |
| `runtime` | Object | `image` and `pythonPackages`. A run does not use it, because the IDE runs every model in its own container. |
| `bridges` | List of strings | Bridge files. A run does not use it, because the bridges of a run are chosen in the run dialog described in [4.5 Running](4.5-running.md). |

The editor reports these problems in a descriptor.

| Code | Severity | Cause |
|---|---|---|
| `descriptor-missing-file` | Error | A named file does not exist, lies in a left-out folder or lies outside the project. |
| `descriptor-invalid` | Error | A named file is of the wrong kind for its key, a value is of the wrong kind, a required key is missing, or a key is written twice. |
| `descriptor-unknown-key` | Warning | The key is not one of the table above. |
| `descriptor-state-machine-form` | Error or warning | An error if an entry with `attachedTo` names an attachable state machine or a fragment, or if an entry without it names an attached one. A warning if the same definition or fragment is listed twice. |
| `deploy-observe-superseded` | Info | The descriptor has `observe`. |
| `deploy-hosting-ignored` | Info | The descriptor has `runtime` or `bridges`. |
| `deploy-tick-delay-range` | Error | `tickDelayMs` is below 0 or above 2147483647. |
| `deploy-tick-delay-zero` | Warning | `tickDelayMs` is 0. The runtime then never waits between ticks. |
| `deploy-event-ttl-never-expires` | Info or warning | An info if `eventTtlMs` is 0, a warning if it is negative. In both cases events never expire. |

### 4.1.2.2 A minimal descriptor

This descriptor runs the model of the lamp example project with only the state machine of the lamp.

```json
{
  "metamodel": "lamp.kmeta",
  "events": "lamp-events.kmeta",
  "model": "lamp.kmodel",
  "stateMachines": [
    { "file": "lamp.kstates", "attachedTo": "lamp" }
  ]
}
```

The descriptor that comes with the lamp example project in `examples/lamp` also attaches `switch.kstates` to
`wallSwitch` and sets the timing.

```json
{
  "metamodel": "lamp.kmeta",
  "events": "lamp-events.kmeta",
  "model": "lamp.kmodel",
  "stateMachines": [
    { "file": "lamp.kstates", "attachedTo": "lamp" },
    { "file": "switch.kstates", "attachedTo": "wallSwitch" }
  ],
  "tickDelayMs": 500,
  "eventTtlMs": 5000
}
```

### 4.1.2.3 Definitions

A state machine of the form `STATEMACHINE "name" ATTACHABLE TO "Type", ...` is not attached to an object by the
descriptor. Its entry has only `file`, and the environment keeps the state machine under its name as a definition.
Objects get instances of a definition through the `behaves after` of their type, through an `ATTACH` clause or
through an `EXCHANGE`. The rules of all three are given in
[2.3.11 State machine management and lifecycle](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#2311-state-machine-management-and-lifecycle).

The descriptor of the spares example project in `examples/spares` attaches the room machine to the room and lists two
definitions.

```json
{
  "metamodel": "spares.kmeta",
  "events": "spares-events.kmeta",
  "model": "spares.kmodel",
  "stateMachines": [
    { "file": "room.kstates", "attachedTo": "room" },
    { "file": "glowing.kstates" },
    { "file": "flickering.kstates" }
  ],
  "tickDelayMs": 500,
  "eventTtlMs": 5000
}
```

The form of each file must fit its entry. An attached state machine needs `attachedTo`, and a definition must not
have it. If the form does not fit, the editor reports `descriptor-state-machine-form` at the file of the entry.

A run uploads the definitions together with the attached state machines, in the order of the descriptor, before it
activates the environment. Because the runtime knows only the definitions that the descriptor lists, every name that
a `behaves after`, an `ATTACH` or an `EXCHANGE` uses must be listed in the descriptor. How a run shows the
instances of the definitions is described in
[4.5.4.7 State machine instances](4.5-running.md#4547-state-machine-instances).

### 4.1.2.4 Creating a descriptor

To create a descriptor, right-click a folder in the *Project* tool window and choose the entry *New Environment File*.
A dialog asks for the name and adds `.kenv.json` to it.

The new descriptor names the files of the current context of the folder. These are the metamodel, the events, the
first model and every state machine. Each state machine is attached to the first object of the type after its
`ATTACHED TO`. If the model has no object of that type, the state machine is attached to the first object of the
model, and if the model has no object at all, to the placeholder `"object"`. An attachable state machine and a fragment
are listed without `attachedTo`.

If the state machines use event domains, the descriptor also gets an `observe` key, although a run does not use it.
The timing keys are left out, and a run of the new descriptor has the default timing of 50 ms between ticks and
3000 ms for an event to wait.

### 4.1.2.5 Fragments

A fragment is listed like a definition, with `file` and without `attachedTo`. A context holds only the fragments that
its descriptor lists, and the container states of its state machines look for their fragments among these. If a
container state uses a fragment that the descriptor does not list, the name after `USE` gets the error
`project.unknown-fragment`. [4.4 Validating](4.4-validating.md) lists this error with the other checks across files.

The pages example project in `examples/pages` composes the state machine of the lamp from three fragments. The
fragment `bulb_test` uses the fragment `wiring_check` in a container state of its own. The state `on` of the lamp holds
a container state that runs `warm_up`. The descriptor of the project lists the three fragments next to the state
machine of the lamp.

```json
{
  "metamodel": "pages.kmeta",
  "events": "pages-events.kmeta",
  "model": "pages.kmodel",
  "stateMachines": [
    { "file": "lamp.kstates", "attachedTo": "lamp" },
    { "file": "bulb_test.frag.kstates" },
    { "file": "wiring_check.frag.kstates" },
    { "file": "warm_up.frag.kstates" }
  ],
  "tickDelayMs": 500,
  "eventTtlMs": 5000
}
```

## 4.1.3 Folders without a descriptor

A folder without a descriptor forms a context of its own from the karpfen files directly inside it that no
descriptor names. The parts of this context follow from the file names.

- The metamodel is the one `.kmeta` file that is not `EVENTS.kmeta`.
- The event metamodel is `EVENTS.kmeta`.
- The models and state machines are all `.kmodel` and `.kstates` files of the folder, the `.frag.kstates` files
  included. An attachable state machine counts as a definition, and a fragment is part of the context. No state
  machine is attached to an object.

Such a context is checked like any other. It cannot be run, though, because *Run > Run* needs a descriptor.

| Situation | Finding |
|---|---|
| Several `.kmeta` files other than `EVENTS.kmeta` | The info `context-multiple-metamodels` on each of them. The first in alphabetical order, ignoring case, is the metamodel. The others belong to no context. |
| No `.kmeta` file other than `EVENTS.kmeta` | The info `context-no-metamodel` on each model and state machine. |

A folder that holds a descriptor forms no context of its own. Its karpfen files that no descriptor names belong to no
context.

## 4.1.4 Files that belong to no context

A file that belongs to no context is still checked. A state machine is read on its own with the language features of
the project, and its errors block a run like the errors of any other file. A model or a metamodel is checked for its
syntax only.

## 4.1.5 The project tree

The *Project* tool window shows the folder in three sections, divided by lines.

1. The project file `.karpfenproject` and the environment descriptors.
2. The folder with the model files and their subfolders.
3. The bridge files.

A double-click or Enter opens a file. A bridge file opens in its form. Once a diagram has a `.vis` file, its model
file can be expanded in the tree, and the `.vis` file shows below it. It opens as text that cannot be edited.

The context menu of the tree has these entries.

| Entry | Effect |
|---|---|
| *New KMeta File*, *New KModel File*, *New KStates File*, *New Fragment File*, *New Environment File* | Asks for a name and creates the file in the folder of the entry, with the suffix added. A new file reads without errors in its context. A new fragment file gets `.frag.kstates` and holds a fragment named after the file, with an initial state, a final state and a transition between them. |
| *Rename…* | Renames the file or folder. Not for the project folder itself. |
| *Delete…* | Deletes the file or folder. Not for the project folder itself. |
| *Reveal in Finder*, *Show in Explorer* or *Show in File Manager* | Shows the file in the file manager of the system. |

Renaming a file does not change the descriptors or the other files that name it. Their references to the old name
have to be changed by hand.

## 4.1.6 The project file

The file `.karpfenproject` in the folder holds the settings of the project. The IDE writes it only when one of these
settings changes, and a folder whose settings were never changed has no such file. It is plain text with one
`key = value` per line, and a line that starts with `#` is a comment. The file can be edited by hand and kept in
version control.

```text
# karpfen project settings. karpfen IDE reads and rewrites this file.
theme = dark
zoom = 110
editorFontSize = 14
pane.runtime = shown 400
open = lamp.kstates
open = lamp.kmeta
active = lamp.kstates
bridge = http.kbridge.json
capture = on
feature.parallel = on
feature.trueParallel = on
```

| Key | Value |
|---|---|
| `theme` | `light`, `dark` or `system`. |
| `zoom` | The scale of the whole window in percent, from 70 to 200. |
| `editorFontSize` | The font size of the editors, from 8 to 40. The default is 13. |
| `pane.project`, `pane.outline`, `pane.problems`, `pane.output`, `pane.runtime` | `shown` or `hidden`, then the size of the tool window. The default sizes are 260, 240, 200, 180 and 400. `pane.output` is the *Language Tools Output*. `pane.runtime` ends in `detached` when the *Runtime* tool window has the window of its own that [4.5.4 The Runtime tool window](4.5-running.md#454-the-runtime-tool-window) describes. |
| `open` | An open file, relative to the folder. One line per tab, in the order of the tabs. |
| `active` | The file of the active tab. |
| `bridge` | A bridge that was ticked in the last run dialog. One line per bridge. |
| `capture` | `on` when the checkbox *Capture run to file* was ticked in the last run dialog. Without the line it is off. |
| `feature.<id>` | `on` for a language feature or a feature of the project that is switched on. Without the line the feature is off. The features are listed in [4.1.7 Language features](#417-language-features). |

A value that makes no sense is dropped, and the default holds in its place. When the IDE writes the file, it keeps the
lines with keys that it does not know.

## 4.1.7 Language features

Five parts of the state machine language are optional. They are switched on by hand for each project, and in a new
project all of them are off.

| Feature | Id in `.karpfenproject` | Reference |
|---|---|---|
| Histories | `history` | [2.3.7 Histories](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#237-histories) |
| Tick limits | `tickLimit` | [2.3.8 Tick limits](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#238-tick-limits) |
| Breakpoints | `breakpoints` | [2.3.9 Breakpoints](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#239-breakpoints) |
| Macros | `macros` | [2.3.6 Macros](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#236-macros) |
| Splits and joins | `parallel` | [2.3.4.3 Splits and joins](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#2343-splits-and-joins) |

The submenu *Run > Language Features* has one entry per feature. The caption of an entry says what a click on it does,
for example *Switch On Histories* while histories are off and *Switch Off Histories* while they are on. The IDE writes
the change into `.karpfenproject` as a line such as `feature.history = on`. Editing that line by hand has the same
effect.

While a feature is off, every use of it in a state machine is the error `kstates.feature-off`, and the error blocks a
run. Completion and the menus of the diagrams do not propose a feature that is off.

A run switches on the features of the runtime that the switched-on language features need. What each of these runtime
features does is described in
[3.2 Runtime features](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.2-features.md).

| Language feature | Runtime feature |
|---|---|
| Histories | History |
| Tick limits | TickLimit |
| Breakpoints | Breakpoint |

With breakpoints switched on, a run also has the debugger of [4.6 Debugging](4.6-debugging.md).

Below the language features, the submenu holds the features of the project. They are not part of the language. They
change nothing in the texts, in the checks or in completion, and their only effect is that every run switches on a
feature of the runtime.

| Feature | Id in `.karpfenproject` | Needs | Effect |
|---|---|---|---|
| Parallel branches on threads | `trueParallel` | Splits and joins | Every run switches on the runtime feature of [3.2.9 TrueParallel](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.2-features.md#329-trueparallel). It steps the branches of a split at the same time, each on a thread of its own. |

Its entry reads *Switch On Parallel branches on threads* or *Switch Off Parallel branches on threads*. Since the
feature needs splits and joins, the entry is disabled while they are off, and switching them off switches the feature
off as well. If a project file has the line `feature.trueParallel = on` without `feature.parallel = on`, the IDE drops
the line when it reads the file.

With the feature on, the branches run on threads of their own, and the order of the steps within one tick can differ
from run to run. A run that must repeat exactly needs the feature off.

## 4.1.8 Settings and logs outside the project

Outside the project the IDE keeps only the recent folders, the place and size of the window and the place and size of
the detached *Runtime* tool window, in the file `~/.karpfen-ide/settings.json`.

The log of the IDE is written to `~/.karpfen-ide/logs/ide.log` and the log of the language tools to
`~/.karpfen-ide/logs/dsl-tools.log`. The environment variable `KARPFEN_IDE_HOME` names another folder in place of
`~/.karpfen-ide` for both the settings and the logs.

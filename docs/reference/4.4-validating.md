# 4.4 Validating

The IDE checks a project at two depths. While you type, it reads every file and checks it within its context. A
validation goes further and checks the whole project across the files of each context. Because that takes longer, a
validation only happens when you ask for it or start a run.

## 4.4.1 Checks while you type

Once the text has not changed for 300 ms, the editor reports what the readers of the languages find. These are the
syntax errors and the checks of each file against the files it depends on. A model, for example, is checked against
its metamodel, and a state machine against the types and events it names. The editor also checks the environment
descriptors and the contexts of the folder as described in [4.1 Projects](4.1-projects.md).

These problems are underlined in the text and listed in the group *Local* of the *Problems* tool window of
[4.2.6 Problems](4.2-text-editor.md#426-problems).

## 4.4.2 What a validation adds

A validation reads the project again and runs the verifier of the language tools over every context. The verifier
checks the state machines against the domain metamodel, the event metamodel and the model, and it reports every place
where one of these does not hold.

- The paths in actions and conditions exist on the type the state machine is attached to.
- An operation and a value fit what the path leads to.
- The `$(...)` references in `EVAL` code resolve.
- The macro calls fit their macros.
- An event and its fields are known in the domain where they are used.
- Every state can be reached.

The verifier gets every state machine of a context, the attached ones as well as the attachable ones, and checks the
names of the attachable state machines across the files. No two of them may have the same name, and the names after
`behaves after`, after `ATTACH` and in `EXCHANGE` must exist and fit the type at that place. These are the checks of
[2.4.6.4 Attachment](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.4-checks.md#2464-attachment).
A finding about a `behaves after` lies in the metamodel, because the clause is written there. While a state machine
of the context cannot be read, no name is reported as unknown.

The codes of the verifier start with `project.`, for example `project.unknown-path` or `project.unreachable-state`.
[2.4 Checks](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.4-checks.md) lists every
check with its code and severity.

The verifier also gets every fragment of a context. It checks each composition of a state machine with the fragments
that its container states use, directly or through other fragments. Such a composition of pages follows the rules of
[2.3.12 Pages](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#2312-pages),
and its checks are listed in
[2.4.6.5 Pages](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.4-checks.md#2465-pages).

A fragment that the context does not hold is the finding `project.unknown-fragment` at the name after `USE`. A name
after `USE` that is not a fragment is `project.not-a-fragment`, and fragments that use each other are
`project.fragment-cycle`. The other codes of compositions are `project.qualified-name-clash`,
`project.conflicting-macros` and `project.unknown-macro`, and the warning `project.macro-from-other-file`.

A finding lies in the file whose text it concerns. A path that does not exist in a state of a fragment, for example, is
reported in the fragment, even when the verifier found it through the state machine that uses the fragment.

The rules of container states, final states and `DONE` within one file are reported while you type, with codes such as
`kstates.container-use` or `kstates.misplaced-done`.

## 4.4.3 Starting a validation

| To | Do this |
|---|---|
| Validate the project in the window | Click the button *Validate* in the bar below the editor, or choose *Run > Validate Project*. While it runs, the button reads `Validating…`. |
| Validate from a terminal | Run `karpfen-ide validate <folder>` as described in [4.8 Command line](4.8-command-line.md). |

## 4.4.4 The dialog

A validation in the window answers with the dialog *Validate Project*. At the top the dialog gives a summary such as
`2 errors and 1 warning`. For a project without findings the summary is `No problems found.`, and for a project with
only infos it is `No errors or warnings.`

Below the summary the dialog lists every finding of the project, both the problems of the editor and those that only
the validation found. Each finding is a row of the form `<file>:<line>  <message>` in the colour of its severity.
Errors come first, then warnings, then the rest, and each of these groups is sorted by file and line. The rows do not
lead to their places, and *Close* is the only button.

## 4.4.5 The group Global

What only the validation found stays in the group *Global* of the *Problems* tool window after the dialog is closed.
Before the first validation the group reads `Global (not validated yet)`. The button *Validate*, the menu entry
The menu entry *Run > Validate Project* and every run fill the group anew. Between two validations it keeps its
findings, also while you edit.

These findings are not underlined in the text. A double-click on one of them leads to its place.

## 4.4.6 Validation before a run

Every run saves all open files and validates the project before it starts. An error anywhere in the project blocks the
run. This includes an error in a file that the descriptor does not name, for example in a state machine that belongs to
no context. The dialog then opens with the title `Run Blocked: the Project Has Errors`. Warnings and infos do not block
a run, and they open no dialog.

After the validation, the run prepares the deployment and checks what matters only for a run. One such check is
whether every state machine is attached to a key that an object of the model has. A problem found here blocks the run
too. The run is then `blocked`, and the *Log* pane lists the problem under `Findings that block the run`. The other ways
in which a run can end early are listed in [4.5.6 A failed run](4.5-running.md#456-a-failed-run).

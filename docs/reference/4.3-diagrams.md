# 4.3 Diagrams

Each of the three kinds of model file has a diagram. The diagram is drawn from the text, and every change made in the
diagram is an edit of the text. The menu entry *Edit > Undo* takes such an edit back.

| File | Diagram |
|---|---|
| `.kstates`, also a fragment | A statechart with the states and their inner states, the transitions, splits, joins and timeouts. |
| `.kmeta`, also an event metamodel | A class diagram with one box per type and its properties, and the relations as lines. |
| `.kmodel` | An object diagram with one box per object and its values, and the `has` and `knows` relations as lines. |

## 4.3.1 Views

For a file with a diagram, the bar below the editor has the buttons *Text*, *Split* and *Diagram*. *Text* shows only the
text, *Split* shows the text and the diagram side by side, and *Diagram* shows only the diagram. The choice is not
stored in the project file.

While the text has errors, the diagram keeps showing the last text that could be read and carries the note
`The text has errors. This is the diagram of the last text that could be read.` Until the text of a file can be read,
a sentence stands in place of the diagram, for example
`No state machine to draw yet. The diagram appears once the text can be read.`

A text that can be read but declares no state, type or object gives an empty canvas with the note
`Nothing to draw yet. A right-click on the canvas adds the first element.` in its middle. The menu of that canvas adds
the first state, type or root object. For a model file this also holds for a text of nothing but blanks and comments,
although the text editor marks such a text as an error because a model needs its root object.

### 4.3.1.1 Moving around

To move the drawing, drag the empty canvas or scroll. Ctrl+scroll or Cmd+scroll zooms. A corner of the canvas holds a
minus, the zoom in percent, a plus and the button *Fit*. A click on the percent sets the zoom back to 100%, and *Fit*
zooms so that the whole diagram shows. The zoom runs from 20% to 300%. A new diagram is fitted to its pane.

A click on a box selects its name in the text.

## 4.3.2 Reading a statechart

| Element | Drawing |
|---|---|
| Header | A title line in the middle above the drawing. For an attached state machine it reads `ATTACHED TO Lamp`, for an attachable one `glowing ATTACHABLE TO Lamp, Bulb` and for a fragment `bulb_test FRAGMENT`. |
| State | A box with round corners. A state with inner states shows its name in a row at its top, a state without inner states in its middle. |
| Container state | A box like a state without inner states. Below its name a row shows a page mark, a small sheet with a folded corner, and the name of the fragment the state uses, or `No fragment set` for a state that names none. The inner states are those of the fragment, drawn in the diagram of the fragment. |
| Final state | A box like a state, with a ring around a dot in its upper right corner. |
| Initial state | A filled dot above the state. |
| Transition | A line from the source state to the target state, ending in an arrowhead. |
| Caption of a transition | The priority and a label made from the condition, for example `1: switch/press`. The priority is the place of the transition in the text. A transition without a condition shows the priority only. |
| Split, join | A filled bar. The lines from the source states lead into the bar without an arrowhead, and the lines from the bar to the target states end in arrowheads. |
| Timeout | A dashed line from the state to the state its timeout leads to, with the caption `after 10 ticks` or `after 1 tick`. |
| Shallow history | A small circle with `H` behind the name of the state. |
| Deep history | A small circle with `H*` behind the name of the state. |
| Breakpoint at entry, at exit | A dot in the error colour on the left border of the state for its entry, on the right border for its exit. |
| Breakpoint at start, at end | A dot in the error colour in front of the caption of the transition for its start, behind it for its end. |
| Code | A small circle with a plus. In a state it is followed by the word `limit` for the tick limit, `entry` for the entry actions or `do` for the do actions. On a transition it stands at the right end of the caption and holds the condition. |

The label of a condition is made of its clauses.

| Clause | Label |
|---|---|
| `EVENT("switch", "press")` | `switch/press` |
| `VALUE("p")` | `p` |
| `EVAL { return x > 1 }` | `[x > 1]` |
| `DONE` | `DONE` |

Several clauses are joined by ` & `. A label longer than 40 characters is cut and ends with `…`. The mark
`NOT LOOPING` is not drawn.

The title line shows the header of the text and changes with it. Since the header is written in the text, the line
cannot be edited, moved or selected in the diagram. It always stands above the topmost element and moves up when a
state is dragged above it. Its place is not stored in the `.vis` file described in
[4.3.8 Arranging by hand](#438-arranging-by-hand).

## 4.3.3 Reading a class or object diagram

| Element | Drawing |
|---|---|
| Type | A box with the name of the type at the top and, below a line, one row per property such as `watts: number`. A type that behaves after an attachable state machine names it in its first row, for example `behaves after glowing`. |
| Object | A box with the underlined title `key : Type` at the top and, below a line, one row per property value such as `watts = 0`. Long values are cut with `…`. |
| `has` relation | A line with a filled diamond at the box that has the other. |
| `knows` relation | A line that ends in an open arrowhead at the box that is known. |
| Label of a relation | The name of the relation, with ` [*]` behind it for a list. |

A relation to a type that the file does not declare is shown as a row in the box of the type that has the relation. A
`knows` to a key that the model does not have is shown as a row in the box of its object in the same way. The class
diagram shows only the types of its own file.

## 4.3.4 Editing a statechart

A right-click on a state, on a line or its caption, on a timeout or on the empty canvas opens a menu of the changes that
fit there.

Some changes need one or more states. For these a prompt such as
`Click the state the transition leads to. Right-click to cancel.` appears, the states to choose from are marked, and
you click one of them. A right-click or a click beside the states cancels the change. The entry *Rename* and the
other entries that need a name open a field at the pointer, filled with the current value.

An entry that writes a construct of one of the optional
[4.1.7 Language features](4.1-projects.md#417-language-features) shows only while the feature is on. An entry that
removes such a construct always shows. After a feature has been switched off, every use of it is an error, and the
entry still takes such a construct out.

The examples below start from this state machine.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "on" {
            STATE "full" { }
            STATE "dimmed" { }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

### 4.3.4.1 On the canvas

| Entry | Shown | Effect on the text |
|---|---|---|
| *Add state* | Always | Adds `STATE "state" { }` at the end of `STATES`, drawn where you clicked. The name is `state`, or `state 2` and so on if the name is taken. |
| *Add initial state* | When no state of the file is initial | Adds `INITIAL STATE "state" { }` in the same way. A file has one initial state at any depth, by the rule of [2.3.2.2 The initial state](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#2322-the-initial-state). |
| *Add container state* | Always | Adds `CONTAINER STATE "container" { }` at the end of `STATES`, drawn where you clicked, or `container 2` and so on if the name is taken. It has no fragment yet, as described in [4.3.4.5 Pages](#4345-pages). |
| *Add final state* | In a fragment | Adds `FINAL STATE "done" { }` at the end of `STATES`, or `done 2` and so on if the name is taken. |
| *Add transition* | When there are states | Asks for the start, then the target, and adds a transition without a condition at the end of `TRANSITIONS`. A final state is never a start. |
| *Add split* | Splits and joins on, at least three states | Asks for the start and two targets, and adds `SPLIT "a" -> "b", "c" { }`. A final state is never the start. |
| *Add join* | Splits and joins on, at least three states | Asks for two starts and the target, and adds `JOIN "a", "b" -> "c" { }`. A final state is never a start. |
| *Edit macros* | Macros on | Opens the inside of the `MACROS` block in a code cell. Code saved into an empty cell creates the block. |

The entry *Add state* on the canvas of the example adds the line `STATE "state" { }` at the end of `STATES`.

```kstates
    STATES {
        INITIAL STATE "off" { }
        STATE "on" {
            STATE "full" { }
            STATE "dimmed" { }
        }
        STATE "state" { }
    }
```

Choosing *Add transition* on the canvas and clicking first `full` and then `dimmed` adds
`TRANSITION "full" -> "dimmed" { }` at the end of the transitions.

```kstates
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "full" -> "dimmed" { }
    }
```

### 4.3.4.2 On a state

| Entry | Shown | Effect on the text |
|---|---|---|
| *Open page NAME* | On a container state that names a fragment | Opens the diagram of the fragment as described in [4.3.4.5 Pages](#4345-pages). The text does not change. |
| *Rename* | Always | Renames the state in its declaration, in every transition and in every timeout that names it. A `"` in the new name becomes `'`. |
| *Edit as text* | Always | Opens the whole state in a code cell titled `State <name>`. |
| *Set fragment* | On a container state | Opens a field with the name of the fragment, empty for a state without one, and writes what you type after `USE`, or `USE "name"` behind the name of the state. An empty field takes `USE` out. The name is not checked against the files of the project. |
| *Make plain state* | On a container state | Takes `CONTAINER` and `USE "name"` out. A history goes too, and so does `DONE` on what leaves the state, as described in [4.3.4.5 Pages](#4345-pages). |
| *Make container state* | Not on a container or final state, the state has no `ENTRY`, no `DO` and no inner states | Writes `CONTAINER ` in front of `STATE`. The state has no fragment yet, and the rest of it stays as it is. |
| *Add inner state* | Not on a container or final state | Adds `STATE "state" { }` at the end of the state's body. |
| *Add inner container state* | Not on a container or final state | Adds `CONTAINER STATE "container" { }` at the end of the state's body. |
| *Add transition from here* | Not on a final state | Asks for the target, and adds a transition without a condition. |
| *Add entry actions* | The state has no `ENTRY`, not on a container or final state | Adds `ENTRY { }` after the breakpoints and the tick limit of the state. |
| *Add do actions* | The state has no `DO`, not on a container or final state | Adds `DO { }` after the entry actions. |
| *Make initial state* | The state is not initial, not on a final state | Writes `INITIAL ` in front of the state and takes it from the state that had it before. That state may stand anywhere in the file. |
| *Remember the last inner state (shallow history)* | Histories on, the state has inner states or is a container state | Writes `SHALLOW HISTORY ` in front of `STATE`, or of `CONTAINER STATE`. |
| *Remember the last innermost state (deep history)* | Histories on, the state has inner states or is a container state | Writes `DEEP HISTORY ` in the same place. |
| *Remove history* | The state has a history | Takes the history words out. |
| *Add tick limit* | Tick limits on, the state has none, not on a final state | Adds `TICK LIMIT { DELAY: 1 TICK }` after the breakpoints of the state. |
| *Add breakpoint at entry*, *Remove breakpoint at entry* | Add needs breakpoints on | Writes or changes `BREAKPOINT { ENTRY }` as the first line of the body. A block without words is taken out. |
| *Add breakpoint at exit*, *Remove breakpoint at exit* | Add needs breakpoints on | The same with `EXIT`. |
| *Make outer state* | The state is an inner state | Moves the state with its inner states to the top level. |
| *Make inner state of* | Another state can take it, not on a final state | Asks for the new outer state and moves the state with its inner states into it. A container state or a final state never takes a state. |
| *Delete state* | Always | Deletes the state, its inner states and every transition that names one of them. |

The empty room inside a state with inner states belongs to that state.

In the menu of the state `off`, *Add entry actions* writes an empty `ENTRY` block into the state.

```kstates
        INITIAL STATE "off" {
            ENTRY { }
        }
```

With breakpoints switched on, the entry *Add breakpoint at entry* of the state `on` puts `BREAKPOINT { ENTRY }` in
front of its inner states.

```kstates
        STATE "on" {
            BREAKPOINT { ENTRY }
            STATE "full" { }
            STATE "dimmed" { }
        }
```

With histories switched on, *Remember the last inner state (shallow history)* in the menu of `on` writes
`SHALLOW HISTORY` in front of the state and changes nothing else.

```kstates
        SHALLOW HISTORY STATE "on" {
            STATE "full" { }
            STATE "dimmed" { }
        }
```

*Make outer state* in the menu of `dimmed` moves that state to the top level.

```kstates
    STATES {
        INITIAL STATE "off" { }
        STATE "on" {
            STATE "full" { }
        }
        STATE "dimmed" { }
    }
```

Renaming `off` to `dark` through its entry *Rename* changes the declaration and both transitions.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "dark" { }
        STATE "on" {
            STATE "full" { }
            STATE "dimmed" { }
        }
    }
    TRANSITIONS {
        TRANSITION "dark" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "on" -> "dark" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

### 4.3.4.3 On a transition

A transition is hit on its line or on its caption.

| Entry | Shown | Effect on the text |
|---|---|---|
| *Edit as text* | Always | Opens the whole transition in a code cell titled `Transition <caption>`. |
| *Wait until the fragment is done (DONE)* | The transition or split leaves a container state, or a source of the join is one, and the condition has no `DONE` | Writes `DONE` as the first clause of the condition. A transition without a condition gets `CONDITION { DONE }` after its breakpoints. |
| *Remove DONE* | The condition has `DONE` | Takes `DONE` out. A condition that holds nothing else goes as a whole. |
| *Add target* | Splits and joins on, on a split | Asks for a state and adds it to the targets of the split in the form `, "x"`. |
| *Add source* | Splits and joins on, on a join | Asks for a state and adds it to the sources of the join. A final state is never a source. |
| *Move earlier, to priority N* | Not on the first transition | Swaps the transition with the one before it in the text. |
| *Move later, to priority N* | Not on the last transition | Swaps the transition with the one after it. |
| *Mark as not looping*, *Allow looping* | Always | Writes ` NOT LOOPING` behind the states, or takes it out. |
| *Add breakpoint at start*, *Remove breakpoint at start* | Add needs breakpoints on | Writes or changes `BREAKPOINT { START }` as the first line of the body. |
| *Add breakpoint at end*, *Remove breakpoint at end* | Add needs breakpoints on | The same with `END`. |
| *Delete transition* | Always | Deletes the transition. |

The menu entry *Mark as not looping*, chosen on the first transition, writes `NOT LOOPING` behind the names of its
two states.

```kstates
        TRANSITION "off" -> "on" NOT LOOPING {
            CONDITION { EVENT("switch", "press") }
        }
```

With breakpoints switched on, the entry *Add breakpoint at start* of the same transition puts a `BREAKPOINT` block
above the condition.

```kstates
        TRANSITION "off" -> "on" {
            BREAKPOINT { START }
            CONDITION { EVENT("switch", "press") }
        }
```

### 4.3.4.4 On a timeout

A timeout is written in the tick limit of its state, for example `TIMEOUT: AFTER 10 TICKS TRANSITION TO "off"`.
Unlike a transition it has no priority, no looping mark and no breakpoints.

| Entry | Shown | Effect on the text |
|---|---|---|
| *Edit tick limit as text* | Always | Opens the inside of the tick limit in a code cell. It is the same cell that the marker of the tick limit opens. |
| *Lead to another state* | Tick limits on | Asks for a state and changes the name after `TRANSITION TO`. |
| *Remove timeout* | Always | Takes the timeout out of the tick limit. A tick limit that is left without a delay is removed as a whole. |

No menu entry adds a timeout. To add one, write it into the tick limit through the code cell of the tick limit.

### 4.3.4.5 Pages

A container state runs a fragment as its inner states. The fragment is a state machine in a file of its own, a page
in the sense of
[2.3.12 Pages](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#2312-pages).
Since the statechart draws each file on its own, the inner states of a container state are not drawn inside it. They
form a page of their own, the diagram of the fragment. How a container state differs from a state with inner states is
described in
[2.3.13 Compound states and container states](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#2313-compound-states-and-container-states).

The entry *Open page NAME* in the menu of a container state, or a double-click on the state, opens the file of its
fragment and shows its diagram. The diagram of the fragment is shown next to the text or alone, in the same way as the
diagram the page was opened from. The fragment is found by its name, and a fragment of the context of the file comes
first. If no file of the project declares the name, a dialog says so and nothing opens. A container state without a
fragment has no page, so its menu has no *Open page* entry and a double-click on it does nothing.

A container state is added with one click, whether the project has fragments or not. The entries
*Add container state*, *Add inner container state* and *Make container state* write it without `USE`, and the diagram
shows `No fragment set` beside the page mark where a container state otherwise names its fragment. Until a fragment is
set, dsl-tools reports such a state with the error `kstates.container-use` of
[2.4.5 KStates](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.4-checks.md#245-kstates).
That error is the expected state of a model in the middle of the usual order of work.

1. Add the container state with *Add container state*, *Add inner container state* or *Make container state*. The
   state is in error from now on.
2. Create the fragment with *New Fragment File* in the context menu of the *Project* tool window, as described in
   [4.1.5 The project tree](4.1-projects.md#415-the-project-tree), and give it its states.
3. Choose *Set fragment* in the menu of the container state and type the name of the fragment. The entry writes `USE`
   with that name and thereby ends the error.

A right-click on `No fragment set` or on the name of a fragment opens the menu of the container state, because the row
lies inside the box of the state. *Set fragment* opens a field at the pointer that holds the name of the fragment, or
nothing for a state without one. The IDE writes whatever name is typed and does not look for it among the files of the
project, so the fragment can also be named before its file exists. Until a file declares the name, dsl-tools reports
it with the error `project.unknown-fragment` of
[2.4.6 Project](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.4-checks.md#246-project).
An empty field takes `USE` and the name out again, and the state shows `No fragment set`.

*Make plain state* turns a container state back into a state without inner states, and it changes more than the
words `CONTAINER` and `USE` because the language allows some things only around a container state. A history goes,
since a state without inner states has nothing to remember. `DONE` goes from every transition and split that leaves
the state, and from a join of which the state was the only container state among the sources. On a join with another
container state among its sources, `DONE` stays. A condition that held nothing but `DONE` is taken out as a whole, as
by *Remove DONE*.

The diagram of a fragment has a bar above the drawing. It reads `Used by:` followed by the names of the files whose
container states use the fragment. A click on a name opens that file and shows its diagram in the same way. For a
fragment that no file uses, the bar reads `No state machine uses this fragment.`

The examples below start from `lamp.kstates` of the pages example project in `examples/pages`. The canvas entry
*Add container state* adds the line `CONTAINER STATE "container" { }` at the end of `STATES`.

```kstates
        CONTAINER STATE "container" { }
```

*Set fragment* in the menu of the new state, with `warm_up` typed into the field, writes the name behind the name of
the state.

```kstates
        CONTAINER STATE "container" USE "warm_up" { }
```

On the transition from `self test` to `off`, *Remove DONE* takes the whole condition out, because that condition holds
nothing but `DONE`.

```kstates
        TRANSITION "self test" -> "off" {
        }
```

*Make container state* in the menu of `steady` writes `CONTAINER` in front of the state and nothing behind its name.

```kstates
            CONTAINER STATE "steady" { }
```

*Make plain state* in the menu of `self test` makes it a state without inner states. The transition to `warming` keeps
the other clause of its condition, and the transition to `off` loses its condition because it held nothing but `DONE`.

```kstates
    STATES {
        INITIAL STATE "off" { }
        STATE "self test" { }
        STATE "on" {
            CONTAINER STATE "warming" USE "warm_up" { }
            STATE "steady" { }
        }
    }
```

```kstates
        TRANSITION "self test" -> "warming" {
            CONDITION {
                VALUE("bulb->lit")
            }
        }
        TRANSITION "self test" -> "off" {
        }
```

In `bulb_test.frag.kstates` the transition from `wiring` to `failed` already has a clause, and
*Wait until the fragment is done (DONE)* in the menu of that transition writes `DONE` in front of it.

```kstates
        TRANSITION "wiring" -> "failed" {
            CONDITION { DONE EVENT("service", "smash") }
        }
```

## 4.3.5 Editing a class diagram

A right-click on a type, on one of its rows, on the line or the label of a relation, or on the empty canvas opens a menu
of the changes that fit there. As in the statechart, an entry that needs another type shows a prompt and marks the
types you can click. An entry that needs a name, a type or a description opens a field at the pointer that holds the
current value. Enter writes what you typed into it, while Escape closes it without a change.

The entries of a type or a row depend on that element alone, never on the other types of the file or on other files.
Since the IDE does not look up the names you type and offers no list of them, a relation can lead to a type that does
not exist yet, and a type can behave after a state machine that is still to be written. A change may leave the
metamodel in error, for example with an empty name, with two types of the same name or with a property of the type
`colour`. The diagram still shows such a text while dsl-tools reports the error in the *Problems* tool window.
A `"` in a name or a value becomes `'`.

Where the file declares the target type of a relation, the relation is drawn as a line. Where it does not, the relation
is a row of its type. Both have the same menu entries, and a row has *Move up* and *Move down* in addition.

The examples start from this metamodel.

```kmeta
type "Bulb" "A light bulb" {
    prop("watts", "number")
    prop("lit", "boolean")
}
type "Lamp" "A lamp" {
    has("bulb", "Bulb")
}
```

### 4.3.5.1 On the canvas

On the canvas, *Add type* adds a type as the first type of the file. The root type of a metamodel is its last type,
and a type added at the top leaves it unchanged. The name of the new type is `Type`, or `Type2` and so on if the name
is taken. On the canvas of a metamodel without types, which shows the note
`Nothing to draw yet. A right-click on the canvas adds the first element.` in its middle, *Add type* writes the first
type of the file.

```kmeta
type "Type" "" {
}
type "Bulb" "A light bulb" {
    prop("watts", "number")
    prop("lit", "boolean")
}
type "Lamp" "A lamp" {
    has("bulb", "Bulb")
}
```

### 4.3.5.2 On a type

| Entry | Shown | Effect on the text |
|---|---|---|
| *Rename* | Always | Renames the type and every relation of the file that leads to it. |
| *Edit as text* | Always | Opens the whole type in a code cell. |
| *Describe* | Always | Opens a field with the description of the type, its second string, and writes the edited text back. |
| *Behaves after* | Always | Opens a field with the name in the clause `behaves after "name"` of [2.1.8 Behaviour of a type](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.1-kmeta.md#218-behaviour-of-a-type), empty for a type without the clause. A name changes the clause or adds it after the description, and an empty field takes the clause out. |
| *Add property* | Always | Asks for the name and adds `prop("name", "string")` at the end of the type. |
| *Add has relation to* | Always | Asks for the target type, which may be the type itself, and adds a relation such as `has("bulb", "Bulb")`. The relation is named after the target with a lower-case first letter, and with a number if the name is taken. |
| *Add knows relation to* | Always | The same with `knows`. |
| *Make root type* | Not on the last type | Moves the type to the end of the file, because the last type is the root type. |
| *Delete* | Always | Deletes the type and every relation of another type that leads to it. |

The two entries that add a relation need a click on a type of the diagram. The entry *Set target type* of a relation,
described in [4.3.5.3 On a row or a line](#4353-on-a-row-or-a-line), takes any name. To let a relation lead to a type
that the file does not declare yet, add it with any type as the target and type the missing name into that field.

Since `Lamp` already has a relation `bulb`, the new relation is named `bulb2` when *Add has relation to* is chosen on
`Lamp` and `Bulb` is clicked as the target.

```kmeta
type "Lamp" "A lamp" {
    has("bulb", "Bulb")
    has("bulb2", "Bulb")
}
```

If the type `Bulb` is renamed to `Light` with *Rename*, the type and the relation that leads to it change.

```kmeta
type "Light" "A light bulb" {
    prop("watts", "number")
    prop("lit", "boolean")
}
type "Lamp" "A lamp" {
    has("bulb", "Light")
}
```

The entry *Behaves after* of the type `Bulb` opens an empty field, and the answer `glowing` adds
`behaves after "glowing"` after the description.

```kmeta
type "Bulb" "A light bulb" behaves after "glowing" {
    prop("watts", "number")
    prop("lit", "boolean")
}
```

### 4.3.5.3 On a row or a line

A row of a type shows a property, a relation whose target type the file does not declare, or the clause
`behaves after`. The clause stands in the header of the type and is no statement of its body, which is why no other
row moves past it. A relation to a declared type is hit on its line or on its label.

| Place | Entry | Shown | Effect on the text |
|---|---|---|---|
| A property | *Rename* | Always | Renames the key of the property. |
| A property | *Set type* | Always | Opens a field with the type and writes what you type in its place. A list stays a list. |
| A property or a relation | *Make list* | It holds one value | Writes `list(...)` around the type, as in `prop("watts", list("number"))`. |
| A property or a relation | *Make single value* | It holds a list | Takes `list(...)` away. |
| A row | *Move up* | The row above shows a property or a relation | Swaps the statement with the one of the row above. A relation drawn as a line between the two stays in its place. |
| A row | *Move down* | There is a row below | The same with the row below. |
| A row | *Edit as text* | Always | Opens a one-line field with the statement behind the row, such as `prop("watts", "number")`. |
| A property | *Delete* | Always | Deletes the statement. |
| A relation | *Rename relation* | Always | Renames the relation. |
| A relation | *Set target type* | Always | Opens a field with the target type and writes what you type in its place. A list stays a list. |
| A relation | *Make knows relation* | On a `has` relation | Writes `knows` in place of `has`. |
| A relation | *Make has relation* | On a `knows` relation | Writes `has` in place of `knows`. |
| The line of a relation | *Edit as text* | Always | Opens the relation in a code cell titled `Relation <name>`. |
| A relation | *Delete relation* | Always | Deletes the relation. |
| The row `behaves after glowing` | *Behaves after* | Always | Opens a field with the name of the state machine and changes the name in the clause. An empty field takes the clause out. |
| The row `behaves after glowing` | *Remove behaves after* | Always | Takes the clause out of the header of the type. |

*Make list* in the menu of the row `watts: number` writes `list` around the type, and the row then reads
`watts: list(number)`.

```kmeta
type "Bulb" "A light bulb" {
    prop("watts", list("number"))
    prop("lit", "boolean")
}
```

*Move down* on the same row puts the property below `lit`.

```kmeta
type "Bulb" "A light bulb" {
    prop("lit", "boolean")
    prop("watts", "number")
}
```

When `Socket` is typed into the field of *Set target type* on the line of `bulb`, the relation leads to a type that the
file does not declare. The line disappears, and until a type `Socket` is added, `Lamp` shows the row `bulb: Socket`
in its place.

```kmeta
type "Lamp" "A lamp" {
    has("bulb", "Socket")
}
```

## 4.3.6 Editing an object diagram

The menus of an object diagram work like those of a class diagram. Again the entries of an object or a row depend on
that element alone. Because a type and the key of the object that a `knows` leads to are typed as text and not looked
up, a reference can name an object that is still to be added. dsl-tools reports an object of an unknown type, a key
that two objects have and a value that does not fit its property in the *Problems* tool window.

A `has` statement is always drawn as a line. A `knows` statement is a line when an object of the model has the key it
names, and a row of its object when no object has that key.

The examples start from this model of the metamodel in
[2.2 KModel](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.2-kmodel.md).

```kmodel
make object "room":"Room" {
    has("lamp") -> make object "lamp":"Lamp" {
        prop("mode") -> "off"
        has("bulb") -> make object "bulb":"Bulb" {
            prop("watts") -> "0"
        }
    }
    has("switch") -> make object "wallSwitch":"Switch" {
        prop("presses") -> "up"
    }
}
```

### 4.3.6.1 On an object

| Entry | Shown | Effect on the text |
|---|---|---|
| *Rename* | Always | Renames the key of the object and every `knows` that leads to it. |
| *Edit as text* | Always | Opens the whole object in a code cell. |
| *Set type* | Always | Opens a field with the type of the object and writes what you type in its place. |
| *Add property* | Always | Asks for the name and adds `prop("name") -> ""` at the end of the object. |
| *Add object* | Always | Asks for the relation, then for the type, and adds `has("relation") -> make object "relation":"Type" { }`. The key of the new object is the name of the relation, with a number if the key is taken. |
| *Add reference to* | Always | Asks for the object, which may be the object itself, and adds `knows("ref") -> "key"`. The relation is named `ref`, or `ref2` and so on if the object has that name already. |
| *Move into* | Not on the root object | Asks for another object and moves the `has` statement that makes the object, with everything in it, to the end of that object. An object does not move into itself or into an object it holds. |
| *Delete* | Not on the root object | Deletes the `has` statement that makes the object, the objects it holds and every `knows` that leads to one of them. |

The root object is made by no `has` statement, which is why it has neither *Move into* nor *Delete*. If *Move into*
is chosen on an object and the object that holds it is clicked, the object moves to the last place of its owner. This
is the way to change the order of the embedded objects of a list relation in the diagram.

The entry *Add object* of `lamp` asks for the relation and then for the type. The answers `spare` and `Bulb` make the
new object `spare` inside `lamp`.

```kmodel
    has("lamp") -> make object "lamp":"Lamp" {
        prop("mode") -> "off"
        has("bulb") -> make object "bulb":"Bulb" {
            prop("watts") -> "0"
        }
        has("spare") -> make object "spare":"Bulb" { }
    }
```

*Add reference to* in the menu of `lamp` asks for the object that `lamp` knows. A click on `wallSwitch` writes
`knows("ref") -> "wallSwitch"` into `lamp`. *Rename relation* on the new line then gives the relation the name
`control` that the metamodel declares.

```kmodel
    has("lamp") -> make object "lamp":"Lamp" {
        prop("mode") -> "off"
        has("bulb") -> make object "bulb":"Bulb" {
            prop("watts") -> "0"
        }
        knows("ref") -> "wallSwitch"
    }
```

*Move into* in the menu of `bulb`, followed by a click on `wallSwitch`, moves the bulb with its value into the switch.
Because the switch of the metamodel has no relation `bulb`, dsl-tools reports the moved statement until it is renamed
or moved back.

```kmodel
make object "room":"Room" {
    has("lamp") -> make object "lamp":"Lamp" {
        prop("mode") -> "off"
    }
    has("switch") -> make object "wallSwitch":"Switch" {
        prop("presses") -> "up"
        has("bulb") -> make object "bulb":"Bulb" {
            prop("watts") -> "0"
        }
    }
}
```

### 4.3.6.2 On a row or a line

A row of an object shows the value of a property, or a `knows` that names a key no object has.

| Place | Entry | Shown | Effect on the text |
|---|---|---|---|
| A property | *Set value* | Always | Opens a field with the value and writes what you type in its place. |
| A property | *Rename* | Always | Renames the key of the property. |
| A property | *Add value* | Always | Adds `prop("key") -> ""` with the same key right after the statement, as one more element of a list. |
| A row | *Move up* | There is a row above | Swaps the statement with the one of the row above. A statement drawn as a line between the two stays in its place. |
| A row | *Move down* | There is a row below | The same with the row below. |
| A row | *Edit as text* | Always | Opens a one-line field with the statement behind the row. |
| A property | *Delete* | Always | Deletes the statement. |
| A `knows` or a `has` | *Rename relation* | Always | Renames the relation. |
| A `knows` | *Set target* | Always | Opens a field with the key of the object it leads to and writes what you type in its place. |
| A line | *Edit as text* | Always | Opens the statement in a code cell titled `Relation <name>`. The cell of a `has` holds the object it makes. |
| A `knows` | *Delete relation* | Always | Deletes the statement. |
| The line of a `has` | *Delete relation* | Always | Deletes the statement with the object it makes, as *Delete* in the menu of that object does. |

Since the elements of a list property keep the order of their statements, *Move up* and *Move down* change the order
of the list. When the key typed into the field of *Set target* is one that no object has, the line becomes a row. The
row turns back into a line as soon as an object gets that key.

*Add value* on the row `presses = up` of `wallSwitch` adds a second element with an empty value. With the answer
`down`, *Set value* on the new row fills it in.

```kmodel
    has("switch") -> make object "wallSwitch":"Switch" {
        prop("presses") -> "up"
        prop("presses") -> "down"
    }
```

### 4.3.6.3 On the canvas

A model without an object is a text of nothing but blanks and comments. The text editor marks such a text as an error
because a model needs its root object. The object diagram still shows its empty canvas with the note that
[4.3.1 Views](#431-views) quotes.

On that canvas the entry *Add root object* writes the root object with the key `object` and an empty type. Until
*Set type* in the menu of the object gives it a type, dsl-tools reports the empty one. Once the model has its root
object, the canvas has no entries.

```kmodel
make object "object":"" { }
```
## 4.3.7 Code cells

A diagram shows some code folded up behind a marker. This is the tick limit, the entry actions and the do actions of a
state, and the condition of a transition. A click on the marker opens the code in a code cell over the diagram. The
entry *Edit as text* opens a whole state, transition, type, object or relation in the same kind of cell.

| Cell | Title |
|---|---|
| Tick limit | `Tick limit of <state>` |
| Entry actions | `Entry actions of <state>` |
| Do actions | `Do actions of <state>` |
| Condition | `Condition of <sources> to <targets>` |
| *Edit as text* | `State <name>`, `Transition <caption>`, `Relation <name>` or the title of the box |

The head of a cell shows its title and the buttons *Save* and *Close*, and Cmd+Enter / Ctrl+Enter saves as well.
Dragging the head moves the cell, and dragging a side or a corner changes its size. The next cell opens at the size of
the last one.

Saving writes the code between the braces of its block. If the code of a tick limit is deleted, saving takes the tick
limit out of its state. A transition without a condition has an empty cell, and code saved into it becomes
`CONDITION { ... }`. If the code of a condition is deleted, the condition is taken out and the transition keeps an
empty body `{ }`. In a cell of *Edit as text*, saving an empty text deletes the whole construct.

A cell is the text editor working on its part of the file. It completes with Ctrl+M, on Windows also with Ctrl+Space,
shows what a name stands for when the mouse rests on it, and underlines errors and warnings according to the language
features of the project. Like the editor, it completes and checks `ATTACH` and `EXCHANGE` in an action block with the
names of the attachable state machines. A cell shows only the problems of its own code. Go to definition does
nothing in a cell.

If the text of the file changes under an open cell, the cell closes without saving.

## 4.3.8 Arranging by hand

The IDE places every element of a diagram by itself. Dragging an element arranges it by hand.

| Drag | Effect |
|---|---|
| A box | Moves it. |
| The bar of a split or join | Moves the bar. |
| A side or a corner of a state with inner states | Sizes the state. It never gets smaller than its inner states need. |
| The caption or label of a line | Moves the caption. It keeps its distance to the line when the line moves. |
| A waypoint | Moves the waypoint and bends the line. |

While you drag, a grid of dots shows, and the element moves from point to point of the grid. A right-click on a line
gives the menu entry *Add waypoint*, and a right-click on a waypoint gives *Remove waypoint*. The waypoints of a line
show while the pointer is near the line. A split or join has a line from each of its states to its bar, and each of
these lines bends on its own.

The first change by hand fixes every element where it is, and from then on the IDE places only new elements. The
arrangement is kept in a file next to the model file, named like it with `.vis` added, for example `lamp.kstates.vis`.
It is a JSON file that the IDE writes, and it opens read-only.

The text always wins over the `.vis` file. What the `.vis` file says about an element that the text no longer has is
dropped. To go back to the automatic layout, delete the `.vis` file.

## 4.3.9 Renaming between diagram and text

A rename in the diagram renames the element in the text, and the element keeps its place in the diagram. The IDE also
recognizes a rename of a state, a type or an object in the text, and the element again keeps its place.

A rename stays in its file. Other files that use the name are not changed and must be updated by hand. Examples are a
model that names a renamed type and a descriptor that names a renamed object.

## 4.3.10 While a model runs

While a run is selected in the *Runtime* tool window and observation is on, the statechart of each running state machine
marks its active states with a strong border, and the innermost active state is lightly filled. A fired transition is
not marked.

When several objects run the state machine of the file, for example as the instances of a definition, the statechart
marks the states of one of them. While such a statechart is shown, the bar below the editor has the button row `Live:`
with one button per instance. A button is labelled with the key of its object and the definition, for example
`gen_Bulb_0 (glowing)`. The button of the instance shown is selected, and a click on another button shows that
instance.

At first the statechart shows the instance that the runtime announced first. When the chosen instance ends, the
statechart shows the first instance left, and when none is left, it marks nothing. How instances come and go during a
run is described in [4.5.4.7 State machine instances](4.5-running.md#4547-state-machine-instances).

While a run is paused at a breakpoint, the statechart marks the place of the pause in the warning colour. A state gets
a dashed frame around it. A transition has its lines drawn wide and a dashed frame around its caption and its bar. The
statechart then shows the instance that halted, and the other buttons of the row take no clicks until the run goes on
with one of the commands of [4.6 Debugging](4.6-debugging.md).

A state machine composed of pages runs as the one flat state machine that
[4.5.4.8 Pages](4.5-running.md#4548-pages) describes. The statechart of its own file marks a container state as active
while the run is inside it. The states of the fragment are marked in the statechart of the file of the fragment, under
the names written there.

A fragment can have several uses. Each container state that uses it is a use of its own, and so is each object that
runs it. While the statechart of a fragment is shown, the row `Live:` names every use by the key of the object and the
container state, such as `lamp: self test`, or `lamp: self test/wiring` for a fragment that another fragment uses. For
a fragment the row shows also when there is only one use. At first the statechart shows the first use.

A pause inside a fragment shows in the statechart of the fragment, at the state or transition of the use that halted.
While the run is paused, the statechart shows that use. The statechart of the file around it marks the container state
as active but shows no pause.

## 4.3.11 Limits

- Macros are edited as text only, in the cell of the canvas entry *Edit macros*.
- `ATTACH` and `EXCHANGE` are written in the cells of the entry and do actions. No menu entry adds them.
- No menu entry adds a timeout.
- No menu entry changes the order of statements that the class or object diagram draws as lines. Their order matters
  for the objects of a list relation in a model. *Move into* on an embedded object puts it last when the object that
  holds it is clicked. Any other order is changed with *Edit as text* on the owner.
- A comment between two types, or before or after the root object, is reached only in the text.
- In a model, entries that read a statement, such as *Set value*, *Rename* and *Set target*, find only strings in
  double quotes. On a statement that KModel takes with single quotes they change nothing.
- A rename together with another change in one edit of the text is not recognized as a rename.
- A change of the arrangement cannot be undone, and there is no command that goes back to the automatic layout.
- Renaming or deleting a model file leaves its `.vis` file behind.
- A state whose name contains `/from:` or `/to:`, or ends in `#` and digits, can lose the waypoints of its lines.
- The badge of a history can overlap the code markers in a narrow state.
- The caption of a transition can cover another line.
- The choice of *Text*, *Split* or *Diagram* is not stored in the project file.
- The diagram of a state machine does not show the states of the fragments its container states use. Each fragment has
  its own diagram.
- The bar of the users of a fragment names files by their names only. Two files of the same name in different
  folders read alike there.

# 4.6 Debugging

When the project has the language feature Breakpoints switched on, a run halts at the breakpoints of its state
machines. The debugger then shows where the run halts and lets it go on by one breakpoint or one tick at a time.

## 4.6.1 Switching breakpoints on

Breakpoints are one of the optional [4.1.7 Language features](4.1-projects.md#417-language-features). To switch them
on, choose *Run > Language Features > Switch On Breakpoints*, and the project file gets the line
`feature.breakpoints = on`. While the feature is off, every `BREAKPOINT` block is an error that blocks the run, and a
run has no debugger.

With the feature on, a run switches on the runtime feature Breakpoint of
[3.2 Runtime features](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.2-features.md).

## 4.6.2 Setting breakpoints

A breakpoint is a block in the text of a state machine. Its form is described in
[2.3.9 Breakpoints](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#239-breakpoints).
In a state, `BREAKPOINT { ENTRY EXIT }` halts before the state is entered and before it is left. A block with only one
of the two words halts only there. In a transition, split or join, `BREAKPOINT { START END }` halts before the
transition changes the active states and after it. Here too a block with one word halts only at that point.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" {
            BREAKPOINT { EXIT }
        }
        STATE "on" { }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            BREAKPOINT { START }
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

Breakpoints can also be set in a statechart. The menu of a state has the entries *Add breakpoint at entry* and
*Add breakpoint at exit*, and the menu of a transition has *Add breakpoint at start* and *Add breakpoint at end*. Once a
breakpoint is set, the entry that set it reads *Remove breakpoint at entry*, *Remove breakpoint at exit*,
*Remove breakpoint at start* or *Remove breakpoint at end* instead. All entries of these menus are listed in
[4.3.4 Editing a statechart](4.3-diagrams.md#434-editing-a-statechart).

A breakpoint shows in the statechart as a dot in the error colour.

| Breakpoint | Place of the dot |
|---|---|
| At the entry of a state | On the left border of the state |
| At the exit of a state | On the right border of the state |
| At the start of a transition | In front of the caption of the transition |
| At the end of a transition | Behind the caption of the transition |

## 4.6.3 The debugger line

A run with breakpoints switched on has a third line in the *Runtime* tool window, below the list of runs. It starts with
`Debugger`.

| The line reads | Buttons | Meaning |
|---|---|---|
| `Running` | *Pause* | The run goes on. |
| `Paused before the entry of on in lamp`, `Paused before the exit of off in lamp` | *Resume*, *Step* | The run halts at a breakpoint of a state. The line ends with the key of the object whose instance halted. |
| `Paused before the transition off to on in lamp`, `Paused after the transition off to on in lamp` | *Resume*, *Step* | The run halts at a breakpoint of a transition. The states of a split or join are joined by `and`. |
| `Paused between two ticks` | *Resume*, *Step* | The run halts after a *Pause* or after a *Step* that ended its tick. |

| Command | Key | Effect |
|---|---|---|
| *Pause* | none | The run finishes the tick it is in and then waits. |
| *Resume* | F9 | The run goes on up to the next breakpoint. |
| *Step* | F8 | The run goes on to the next breakpoint or to the end of the tick, whichever comes first. From between two ticks it runs one tick. |

The buttons *Pause*, *Resume* and *Step* are also entries of the *Run* menu. They act on the selected run.

## 4.6.4 What a pause shows

While a run is paused, the open statechart of the state machine marks the place of the pause in the warning colour. A
state gets a dashed frame. For a transition the lines are drawn wide, and its caption and its bar get a dashed frame.
The debugger line names the same place in words. Everything else that the statecharts show of a run is described in
[4.3.10 While a model runs](4.3-diagrams.md#4310-while-a-model-runs).

## 4.6.5 Breakpoints of definitions

A breakpoint in an attachable state machine halts every instance of it, since each object that runs the definition
runs the same text. The debugger line names the object whose instance halted, for example
`Paused before the entry of lit in gen_Bulb_0`. While the run is paused, the statechart of the definition shows that
instance, whichever instance was chosen before. How instances come and go is
described in [4.5.4.7 State machine instances](4.5-running.md#4547-state-machine-instances).

When an instance ends, the runtime forgets what the instance left behind, and a later instance on the same object
starts without it. The rules for this are in
[3.1.13.3 When instances join and leave](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md#31133-when-instances-join-and-leave).

## 4.6.6 Breakpoints in pages

A breakpoint in a fragment halts every use of it, since in the flat state machine of
[4.5.4.8 Pages](4.5-running.md#4548-pages) each container state that uses the fragment runs a copy of its text. The
debugger line names the state by its name in the flat state machine, for example
`Paused before the entry of self test/wiring/measuring in lamp`.

The statechart of the fragment shows the use that halted and marks the place under the name that the fragment gives
it, in the way that [4.3.10 While a model runs](4.3-diagrams.md#4310-while-a-model-runs) describes for runs in pages.

## 4.6.7 Limits

- A run without a window, started from the [4.8 Command line](4.8-command-line.md), has no debugger, and its
  breakpoints never halt it.
- *Pause* has no key.
- A breakpoint takes effect with the next run, because it is part of the uploaded text.

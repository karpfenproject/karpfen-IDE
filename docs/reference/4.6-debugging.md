# 4.6 Debugging

A run halts at the breakpoints of its state machines when the project has the language feature Breakpoints switched
on. The debugger then shows where the run halts and lets it go on, a breakpoint or a tick at a time.

## 4.6.1 Switching breakpoints on

Choose Run > Language Features > Switch On Breakpoints. The project file gets the line `feature.breakpoints = on`, see
[4.1.7 Language features](4.1-projects.md#417-language-features). While the feature is off, every `BREAKPOINT` block is
an error that blocks the run, and a run has no debugger.

With the feature on, the run switches on the runtime feature Breakpoint, see
[3.2 Runtime features](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.2-features.md).

## 4.6.2 Setting breakpoints

A breakpoint is a block of the text, see
[2.3.9 Breakpoints](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#239-breakpoints).
In a state, `BREAKPOINT { ENTRY EXIT }` halts before the state is entered, before it is left, or both. In a transition,
split or join, `BREAKPOINT { START END }` halts before the transition changes the active states, after it, or both.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" {
            BREAKPOINT { EXIT }
        }
        STATE "on" { }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            BREAKPOINT { START }
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

In a statechart, the menu of a state has Add breakpoint at entry and Add breakpoint at exit, and the menu of a
transition has Add breakpoint at start and Add breakpoint at end. Each has a Remove entry once the breakpoint is set,
see [4.3.4 Editing a statechart](4.3-diagrams.md#434-editing-a-statechart). A breakpoint shows as a dot in the error
colour: on the left border of a state for its entry, on the right border for its exit, in front of the caption of a
transition for its start and behind it for its end.

## 4.6.3 The debugger line

A run with breakpoints switched on has a third line in the Runtime tool window, below the list of runs. It starts with
`Debugger`.

| The line reads | Buttons | Meaning |
|---|---|---|
| `Running` | Pause | The run goes on. |
| `Paused before the entry of on in lamp`, `Paused before the exit of off in lamp` | Resume, Step | The run halts at a breakpoint of a state. The line ends with the key of the object whose instance halted. |
| `Paused before the transition off to on in lamp`, `Paused after the transition off to on in lamp` | Resume, Step | The run halts at a breakpoint of a transition. The states of a split or join are joined by `and`. |
| `Paused between two ticks` | Resume, Step | The run halts after a Pause or after a Step that ended its tick. |

| Command | Key | Effect |
|---|---|---|
| Pause | none | The run finishes the tick it is in and then waits. |
| Resume | F9 | The run goes on up to the next breakpoint. |
| Step | F8 | The run goes on to the next breakpoint or to the end of the tick, whichever comes first. From between two ticks it runs one tick. |

Pause, Resume and Step are also in the Run menu. They act on the selected run.

## 4.6.4 What a pause shows

While a run is paused, the open statechart of the state machine marks the place in the warning colour: a dashed frame
around the state, or the lines of the transition drawn wide with a dashed frame around its caption and its bar, see
[4.3.10 While a model runs](4.3-diagrams.md#4310-while-a-model-runs). The debugger line names the place in words.

## 4.6.5 Breakpoints of definitions

A breakpoint in an attachable state machine halts every instance of it, since each object that runs the definition
runs the same text, see [4.5.4.7 State machine instances](4.5-running.md#4547-state-machine-instances). The debugger
line names the object whose instance halted, as in `Paused before the entry of lit in gen_Bulb_0`, and the statechart
of the definition shows that instance while the run is paused, whichever instance was chosen before. The runtime
forgets what an instance left behind when it ends, so a later instance on the same object starts without it, see
[3.1.13.3 When instances join and leave](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md#31133-when-instances-join-and-leave).

## 4.6.6 Limits

- A run without a window has no debugger. Its breakpoints never halt it, see [4.8 Command line](4.8-command-line.md).
- Pause has no key.
- A breakpoint takes effect with the next run, because it is part of the uploaded text.
